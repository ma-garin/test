## 6.1 曖昧な仕様の扱い（期待結果を推測で埋めない・空欄のまま実行しない）

仕様が曖昧で期待結果を 1 つに決められないケースは、`system_test_cases.csv` の「仕様の状態」列（空＝確定）で 4 つに分ける。

| 仕様の状態 | いつ使う | 期待される結果の欄の書き方 | 集計（`test-metrics.sh`） |
|---|---|---|---|
| 確認待ち | 仕様の持ち主に質問を出し、返事が無い | `確認待ち: <質問>（<宛先>・<出した日>）` | 結果が pass / fail でも未実施に数える。1 件でもあれば `--gate` は進めない（判定不能を合格に数えない） |
| 仮置き（根拠付き） | 根拠のある仮の値で先に実行する | `<値>（仮置き。根拠: <規格・類似機能・過去の決定>、期限: <YYYY-MM-DD>）` | 数えるが WARN。期限までに確定させ、状態を空に戻す |
| 範囲外（合意済み） | 今回は検証しないと合意した | `範囲外: <合意した場所（RFD・ADR・議事録）>` | 件数を info で出す。trace-check の C8（テストコード未対応）の対象外 |
| 未定 | 仕様そのものが決まっていない | （テストケースにしない。設計段階で止め、要件の未解決事項・RFD へ戻す） | CSV に残っていれば確認待ちと同じ扱い |

- 確認が返ったら期待結果を確定値に書き換え、「仕様の状態」を空にしてから再実行する（e2e-cycle の「修整確認待ち」は修整の確認で、こちらは仕様の確認。混ぜない）
- 仮置きの根拠が書けないなら確認待ちにする
