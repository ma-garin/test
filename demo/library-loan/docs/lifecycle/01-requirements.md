## 機能要件（REQ-F）

| ID | 要件（EARS 型） | 優先度 | 由来 RFD | 受入基準（観測可能な合格条件） |
|---|---|---|---|---|
| REQ-F-001 |  | Must | RFD-001 |  |
| REQ-F-0xx |  | Should |  |  |

<!-- 採番したら `REQ-F-0xx` を 3桁の連番に置き換える。`-0xx` のままなら trace-check.sh の対象外 -->


- 優先度は MoSCoW（Must / Should / Could / Won't）
- 受入基準は UAT の手順にそのまま書き換えられる粒度で書く（例: ×「使いやすい」 ○「3タップ以内で保存でき、リロード後もデータが残る」）
- 「AかつB」は2要件に分割する

### 要件文の型（EARS。1 要件 1 文。主語はシステム名か画面名）

| 型 | 書式 | 例 |
|---|---|---|
| 常時 | <主語>は、<応答>する。 | 貸出画面は、利用者の貸出中の冊数を表示する。 |
| 〜のとき（When） | <契機>とき、<主語>は<応答>する。 | 利用者が保存を押したとき、システムは入力内容を端末に保存する。 |
| 〜の間（While） | <状態>の間、<主語>は<応答>する。 | オフラインの間、システムは入力を端末に保持する。 |
| 〜の場合（If） | <望まない事象>場合、<主語>は<応答>する。 | 通信に失敗した場合、システムは再送ボタンを表示する。 |
| 〜では（Where） | <機能・構成>では、<主語>は<応答>する。 | 管理者機能を有効にした構成では、システムは操作ログを残す。 |

- 曖昧語（適切に・必要に応じて・など・高速・十分・可能な限り・使いやすい 等）は数値・条件・列挙に置き換える。辞書は `skills/sdd-ecc-workflow/references/ambiguous-words.md`
- 「以下の N 個」と書いたら、列挙の数を N にそろえる（食い違いは req-lint の NG）

## 非機能要件（REQ-N）

ISO/IEC 25010 の品質特性で分類する。既定値は `skills/nfr-standards` のプロジェクト種別（PWA / 単一HTMLツール / Streamlit）から転記し、逸脱する場合のみ理由を書く。

| ID | 特性 | 要件（EARS 型） | 由来 RFD | 判定基準（測定条件付き） |
|---|---|---|---|---|
| REQ-N-001 | 性能効率性 |  | RFD-001 | <!-- 例: 3G相当(1.6Mbps)で初回操作可能まで3秒以内 --> |
| REQ-N-0xx | 使用性 |  |  |  |
| REQ-N-0xx | 信頼性 |  |  |  |
| REQ-N-0xx | セキュリティ |  |  |  |
| REQ-N-0xx | 保守性 |  |  |  |

該当する特性のみ採番する。判定基準は必ず測定条件つきで書く（「速いこと」は不可）。性能・応答・件数・同時・可用・容量の要件に数値と単位が無ければ req-lint の NG（`.claude/phase-gate` があれば基本設計に進めない）。
