# 工程承認記録（approvals/）

各工程の完了を**人間が承認した記録**。`docs/lifecycle/approvals/phase-0.md` 〜 `phase-9.md` に1工程1ファイルで置く。
`./00_導入/02_プロジェクト配布/init-lifecycle.sh <対象>` が `phase-approval.md` から10本を生成する。

## なぜ必要か

AIDD では「プロセスが回っているか」を見ても「**要求したものが確実に作られているか**」には答えられない。
要件の取り違えが基本設計で入り込むと、詳細設計・実装・テストまで全部その上に積まれ、受け入れテストで判明したときの手戻りが最大になる。
各工程の出口で承認を取り、**その承認を成果物の版に縛る**ことで、誤りの伝播を工程1つ分で止める。

## 機械と人間の境界（この線を越えない）

| 機械が判定する（`check-approval.sh`） | 人間しか判定できない |
|---|---|
| 承認記録が存在するか・必須欄が埋まっているか | その設計が**本当にその要件を満たすか** |
| **承認時の版と現在の版が一致するか**（失効検出） | 受入基準の解釈が依頼者の意図と合っているか |
| 未解消の差し戻し事項が残っていないか | 残存リスクを受容してよいか |
| 未確認事項が残ったまま「承認」になっていないか | 条件付き承認の条件が妥当か |
| 全要件が下流 ID に紐づくか（`trace-check.sh`） | |

この線を曖昧にすると「AI が承認した」ことになり、第三者検証としての価値が消える。
**AI は承認しない。AI は人間が判子を押す前に指摘を出し切る役**（`/phase-review <工程番号>`）。

## 使い方

```bash
/phase-review 2                       # AI 3役が順次レビュー → phase-2-ai.md に申し送り
                                      # 指摘を潰してから人間が phase-2.md を埋める
./scripts/phase-hash.py docs/lifecycle/02-basic-design.md docs/lifecycle/traceability-matrix.md
                                      # → 16桁を reviewed_hash に貼る
./scripts/check-approval.sh --phase 2 # exit 0 なら第3工程へ進んでよい
```

## covers に何を入れるか

**その工程が所有する成果物だけ**（`docs/lifecycle/0<n>-*.md`）。
`traceability-matrix.md` は入れない — 全工程が書き足す生きた文書なので、承認に縛ると
後続工程の更新が前工程の承認を毎回失効させ、ゲートが永久に詰まる。
追跡表の整合は `./scripts/trace-check.sh docs/lifecycle`（NG=0）が別の機械ゲートとして担保する。

## 判定は3値

`承認` / `条件付き承認` / `差し戻し`。**未記入は判定値ではなく「未承認」という状態**。

- 条件付き承認: 条件表が空なら判定不能（exit 2）。条件は全て必須で、1つでも未達なら承認ではない
- 差し戻し: 各事項に ID と**解消の検証方法**を必須にする。`未解消` が1件でも残れば承認にできない

## 検査の対象範囲

工程 n が**着手済み**のときだけ承認を要求する。着手判定は「**成果物から `YYYY-MM-DD` のプレースホルダが消えているか**」
（雛形は各ファイルにちょうど1つ持つ）。未着手の工程は未承認のままでよく、NG にならない。

## 強制（任意）

プロジェクトルートに `.claude/phase-gate` を置くと、`block-phase.py` hook が
**前工程が未承認・失効・差し戻し中のまま次工程の成果物を書くこと**を物理的にブロックする。

- `docs/lifecycle/approvals/` 配下への書き込みは常に許可される（承認者が止められては意味がないため）
- **バイパス用の環境変数は用意しない。** 止めたいときは `.claude/phase-gate` を消す（消したことが git 差分に残る）
