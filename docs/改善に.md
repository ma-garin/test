# 画面別・当たり前品質／魅力的品質 提案バックログ

## 結論

現状は、個々の機能が表示されていても、利用者が **「今どの対象を見ているか」「次に何をすべきか」「その操作をしてよいか」** を判断するために、表・KPI・説明文を読み解く必要があります。作り込みが浅く感じる主因は、情報量の不足ではなく、判断から行動までの導線が画面ごとに揃っていないことです。

この文書は、Luna / Haiku のような軽量モデルでも安全に対応できるよう、1チケットを原則「1〜3テンプレート、DB変更なし、既存トークンを使う」に分割した実装バックログです。

## Goal実行用：エージェント運用契約

この文書をGoalの唯一の要件資料として別のAIエージェントへ渡す場合、以下を必ず守る。ここに書かれた実行順・完了条件は、本文の各チケットより優先する。

### 目的

VeriRAG PMO Agentを、**SIerのPMOが複数案件を計画・推進・品質管理・意思決定・報告・監査まで一貫して支援できるシステム**へ段階的に完成させる。

ライブ着地予測は、この目的を実現する中核の差別化機能である。しかし目的の全体ではない。基礎となる案件・タスク・課題・不具合・リスク・変更管理、品質管理、成果物・承認、RAG／チャット、外部連携、テナント・権限・監査、教育・PoC・KPIを、当たり前品質として実用水準にすることを同時に完了させる。

| --- | --- | --- |

### 必ず守る作業順

1. **初期確認**: `docs/UIDesign.md`、`docs/DesignSystem.md`、この文書、関連モデル・ビュー・テストを読む。現在の実装と記載が矛盾する場合、コードを事実として実行ログに差分を記録する。
2. **基礎UI P0**: タスク、課題、不具合、リスク、変更要求、AI提案、RAG検索／チャットの「絞る → 開く → 根拠を確認 → 処理する」導線を先に完成させる。`JT-01`〜`JT-05`は最優先にする。
3. **プロジェクト知識グラフの土台**: `GE-01`（オントロジー・型付き関係）→ `GE-02`（テナント境界・完全性）→ `GE-03`（影響／根拠クエリ）→ `GE-04`（可視化・受入）を実装する。グラフDBはP0の前提にしない。
4. **ライブ着地予測の土台**: `LDF-01`（機能・依存・マイルストーン・勤務日）→ `LDF-02`（Signal・関連・Snapshot）→ `LDF-03`（決定論予測）→ `LDF-04`（画面）の順で実装する。予測は根拠不足なら必ず`算定不能`とする。
5. **既存データの増分連携**: `LDF-05`を実装する。Jira／Redmine、手動／CSVのテスト証跡を読み取り専用で扱い、同期・鮮度・失敗理由を表示する。
6. **会話・開発データ連携**: `LDF-06`〜`LDF-08`を実装する。Slack、テスト管理、Git／CIは、まず正規化したSignalと確認可能な関連候補を作る。外部書込みは行わない。
7. **残る当たり前品質**: 画面別監査のP1/P2を、依存が少ない小チケットから実装する。各完了後に実行ログを更新する。
8. **魅力的品質の検証**: P0/P1、GE-01〜05、LDF-01〜08を満たし、実データまたは安全なサンプルで効果を測れる場合のみ進める。

### 実装・設計の不変条件

- テナント、案件、ロールによる表示・検索・RAG・予測の分離を崩さない。権限外のSignal、会話、文書、予測を絶対に混在させない。
- 外部システムは既定で**外部→内部の読み取り専用**とする。Slack／Jira／Redmine／Git／Confluence／Teamsへ、ユーザーの明示承認なしに投稿・更新・削除しない。
- Slack等の会話はSignalであり、AI候補は候補である。人が確認するまで状態、影響範囲、遅延日数、外部台帳の値を確定しない。
- 期限・遅延／前倒し日数を、欠けた依存・解消見込み・勤務日からもっともらしく補完しない。不足項目、最終取得時刻、確信度、算定不能の理由を表示する。
- 既存の青基調、余白、固定ヘッダー、親ナビゲーション、ページ遷移、オフラインのMaterial Symbols利用を維持する。UIを変える前に既存のデザイン資料に従う。
- 秘密情報・アクセストークン・Webhookシークレット・Slack本文の過剰保存を避ける。資格情報は参照名だけを持ち、ログ・エラー・画面へ値を出さない。
- 既存のユーザー変更を上書きしない。`git reset`、`git checkout --`、広範な削除、依存関係の不用意な更新を行わない。

### 外部連携の実装ポリシー

- 既存の`Connection`、`SyncJob`、`SyncedRecord`を出発点にし、Webhook受信・定期照合・正規化・関連付け・予測再計算を分離する。
- Slackは許可された案件チャンネルのみを対象にする。DM・非許可チャンネル・無期限の全文保存を既定で扱わない。
- Jiraは課題更新とコメント更新を別イベントとして扱う。RedmineはREST増分取得を基本とし、顧客固有のプラグインを必須前提にしない。
- Webhookは再送・順不同・欠落を前提とし、外部イベントID／ハッシュによる冪等化と定期照合を実装する。
- 実運用の認証情報、顧客の本番Slack／Jira／Redmine、外部ネットワークを使って連携を試さない。接続契約、モック、フィクスチャ、単体／統合テストで検証する。実接続は利用者が認可した別工程でのみ行う。

### 各チケットの完了手順

1. 着手前に、対象チケット、変更予定の境界、受入条件、既存テストを実行ログへ書く。
2. 最小の変更で実装する。DB変更が必要な場合は、マイグレーション、テナント境界、既存データの安全な既定値を含める。
3. 外部挙動を検証するテストを追加・更新する。実装詳細だけを固定するテストは避ける。
4. UI変更は、サーバーを起動して対象画面を確認する。現在地・空状態・権限なし・失敗状態・760px幅・200%表示で破綻しないことを確認する。
5. 対象テスト、`manage.py check`、差分の空白エラーを確認する。失敗を隠して次チケットへ進まない。
6. 完了・保留・設計判断を実行ログへ更新し、次の依存解除済みチケットへ進む。

| 4 | 追加承認が必要な事項を実施せず、保留として報告 | **満たす** | 実接続・外部書込み・デプロイは未実施（すべてモックとフィクスチャ）。`test_module_has_no_outbound_http_client` で HTTP クライアントの持ち込みを禁止。権限変更は利用者の指示（選択肢A）を得てから実施し、判断内容を本文へ記録 |

**未達ではないが、次に着手すべき残件**

- `word-break: auto-phrase` は Chrome/Edge のみ対応。Safari・Firefox では和文が語中で折れる。
- `not_implemented.html` はどのビューからも参照されない孤立テンプレートで、実レンダリング未確認。
- 実接続での検証（Slack／Jira／Redmine／CI）は利用者が認可した別工程で行う。

### エージェントループとハーネスの位置付け

このGoalでは、以下の2つを混同しない。

| 区分 | 目的 | 主な構成 | 絶対にしないこと |
| --- | --- | --- | --- |
| **開発エージェント・ハーネス** | この文書に従うAIエージェントが、計画・実装・検証・修正を安全に繰り返す。 | 要件コンテキスト、作業キュー、実行ログ、テストゲート、失敗時の再計画、停止条件。 | テスト未実行の自己申告を完了扱いにすること、外部システムを無断操作すること。 |
| **プロダクト内エージェント・ループ** | 外部Signalから着地予測を更新し、PMOへ根拠・不確実性・次アクションを提示する。 | Signal取込、正規化、関連候補、検証、予測再計算、提案、利用者フィードバック。 | AI候補を確定事実として扱うこと、承認なしで台帳・Slack・外部システムを書き換えること。 |

ループエンジニアリングは、AIに単発指示を出すのではなく、目標に向けて「観察 → 判断 → 実行 → 検証 → 修正」を証跡付きで繰り返す運用設計である。[IBMによる定義](https://www.ibm.com/think/topics/loop-engineering) ハーネスエンジニアリングは、そのループに必要なコンテキスト、権限、ツール、検証、記憶、停止条件を意図的に設計することである。[Martin Fowlerの解説](https://martinfowler.spicytakes.org/post/2026-04-02-harness-engineering)

### 開発エージェント・ループの状態機械

```text
DISCOVER
  → SELECT（依存解除済みの最小チケットを1件選ぶ）
  → PLAN（受入条件・境界・検証方法を実行ログへ書く）
  → IMPLEMENT（最小変更を実装）
  → VERIFY（決定論的チェック → UI／統合確認）
      ├ 成功 → REVIEW（差分・権限・要件との照合）
      │           ├ 承認 → RECORD（証跡・学び・次チケットを記録）→ DISCOVER
      │           └ 差戻し → REPAIR
      └ 失敗 → DIAGNOSE（失敗原因を分類）→ REPAIR
REPAIR
  → 同じ失敗が3回未満: PLANへ戻る
  → 同じ失敗が3回: HOLD（原因・試行・必要な人の判断を記録）→ DISCOVER
COMPLETE
  → Goalの完了判定をすべて満たした場合のみ終了
```

#### ループの不変条件

1. 1周で扱うのは、依存解除済みの最小チケット1件だけにする。巨大な「全画面改善」を1回の実装単位にしない。
2. `VERIFY`の判定は、説明文ではなくコマンド結果、テスト、画面状態、差分確認を優先する。失敗中のテストを削除・弱化して通過させない。
3. `REPAIR`では、直前の失敗証跡と変更差分だけを次のコンテキストへ渡す。無関係なファイルを再読込してコンテキストを膨張させない。
4. `HOLD`は失敗ではない。資格情報、顧客のデータ利用許可、事業上のD判断、再現不能な外部障害を明示し、他の依存しないチケットへ進む。
5. 実行ログはループの外部記憶である。次回のエージェントは、会話履歴ではなく実行ログ、未完了チケット、最新のテスト証跡から再開する。

### 開発エージェント・ハーネスの構成

| 層 | 必要な資産／機能 | このリポジトリでの扱い |
| --- | --- | --- |
| Feedforward（開始時の誘導） | `AGENTS.md`、`改善に.md`、`UIDesign.md`、`DesignSystem.md`、対象チケット、既存テスト。 | エージェントは作業前に必要な資料だけを読み、文書とコードの差分を実行ログへ残す。 |
| 作業キュー | ID、優先度、依存、状態、受入条件、保留理由。 | 本文の`JT-*`、`LDF-*`、画面別P0/P1をキューとし、実行ログで状態を管理する。 |
| 決定論的ガード | Djangoチェック、対象テスト、全体テスト、差分検査、マイグレーション整合性、UIスモーク。 | チケットの種類ごとに最小の検証を選び、終了時にはより広い回帰確認を実施する。 |
| 推論的レビュー | 要件との照合、UIの視認性、根拠・権限・説明可能性のレビュー。 | 決定論的検証に合格した後だけ行う。推論的レビュー単独で完了にしない。 |
| 記憶 | 実行ログ、決定記録、失敗パターン、未解決のD判断。 | 進行中・完了・保留を文書に残し、別セッションでも同じチケットを重複実装しない。 |
| 権限境界 | ファイル編集、ローカルテスト、外部ネットワーク、実接続、デプロイの分離。 | コード・テスト・文書は自律実行可。実接続・外部書込み・デプロイは追加承認まで保留する。 |
| 観測性 | チケット開始／終了、コマンド結果、失敗回数、保留理由、変更範囲。 | 実行ログに短く残す。秘密値・顧客データ・長いログ全文は保存しない。 |

### プロダクト内エージェント・ループ

ライブ着地予測では、常駐AIが自由に考え続けるのではなく、イベントと時間を起点にした有限のループとして実装する。

```text
TRIGGER
  = 外部Signal受信 / 同期完了 / WBS・不具合・見込み更新 / 定時再評価
  → OBSERVE（Signalの検証・鮮度・権限確認）
  → NORMALIZE（正規形へ変換）
  → LINK（ID一致 → 確定リンク → 規則 → AI候補）
  → RECOMPUTE（影響範囲だけを決定論的に再計算）
  → ASSESS（確信度・算定不能・予測差分を評価）
  → PROPOSE（通知・確認依頼・報告差分を下書き化）
  → HUMAN REVIEW（PMO／PM／QAが採用・修正・却下）
  → LEARN（予測と実績、候補の採否を記録）
```

| 制御点 | 実装ルール |
| --- | --- |
| 起動条件 | 任意のチャット入力ではなく、認証済みの外部イベント、同期の成功／失敗、明示更新、定時ジョブだけで起動する。 |
| 冪等性 | `source + external_event_id`またはペイロードハッシュを使い、再送・順不同でSignal、Snapshot、通知を重複作成しない。 |
| デバウンス | 同一のFeature／WBSに短時間で複数イベントが来たとき、再計算をまとめる。ただし重大不具合・期日悪化は待たせない。 |
| 停止条件 | 根拠不足、鮮度切れ、権限不明、循環依存、対応不能な状態値では、推測ループを続けず`算定不能`または確認依頼で終了する。 |
| 書込み境界 | 外部システムへの投稿・更新、社内台帳の状態確定、エスカレーションは人の承認後のみ行う。P0〜P1は読み取り・下書き・通知候補に限定する。 |
| 評価 | 予測日と実績日の誤差、確信度の校正、関連候補の採否、PMOの確認時間、報告差戻しで測る。採用率だけを最適化しない。 |

### グラフエンジニアリング：PMOの知識グラフとエージェントの実行グラフ

グラフエンジニアリングは、この製品では単なるネットワーク図の表示ではない。**PMOが判断する対象間の関係を、型・方向・時点・出所・確認状態つきで設計し、影響・根拠・依存を機械的にたどれるようにすること**である。ループエンジニアリングが「1つのエージェントがどう反復するか」を決めるのに対し、グラフエンジニアリングは「何が関係し、どの経路を通り、どこで止まるか」を明示する。[Graph Engineeringの知識グラフ／タスクグラフの整理](https://github.com/codejunkie99/graph-engineering)

このシステムには、用途の異なる2種類のグラフが必要である。

| グラフ | ノード | エッジ | 使う場面 | 混同しないこと |
| --- | --- | --- | --- | --- |
| **PMO知識グラフ** | 案件、機能、WBS、マイルストーン、不具合、課題、リスク、変更、画面、FE、BE、API、テスト、文書、Signal、予測。 | `depends_on`、`blocks`、`impacts`、`implements`、`tests`、`caused_by`、`evidenced_by`、`discussed_in`、`forecasts`等。 | 影響範囲、遅延伝播、根拠説明、GraphRAG、類似障害の探索。 | 「似ている」ベクトル検索結果を、確定した依存・影響関係にしない。 |
| **エージェント実行グラフ** | 計画、実装、テスト、レビュー、連携取得、正規化、関連付け、再計算、通知、承認等の処理ノード。 | 順次、条件分岐、合流、再試行、人の承認、停止。 | 開発ハーネス、プロダクト内のSignal→予測更新ループ。 | エージェントの処理順を、案件のWBS依存や技術影響と混ぜない。 |

#### PMO知識グラフのオントロジー

| ノード種別 | 一意性・スコープ | 必須プロパティ | 代表的な関係 |
| --- | --- | --- | --- |
| Project | テナント内の案件ID。 | 名称、状態、計画開始／終了、責任者。 | `contains` Feature／WBS／Milestone／Signal。 |
| Feature | 案件内で一意の業務機能。 | 名称、責任者、リリース対象、状態。 | `implemented_by` Component、`planned_by` WBS、`validated_by` TestEvidence、`affected_by` Defect。 |
| WBS Task | 案件内のWBSコード。 | 計画日、実績、残作業、状態、クリティカルパス。 | `depends_on` WBS、`contributes_to` Milestone、`blocks`／`blocked_by` Defect。 |
| Milestone | 案件内のマイルストーン。 | 予定日、予測日、実績日、品質ゲート。 | `requires` WBS、`gates` Feature／TestEvidence。 |
| Defect／Issue／Risk／Change | 案件内の管理台帳ID。 | 状態、重大度、担当、期限、外部キー、更新時刻。 | `affects` Feature／Component／WBS、`caused_by` Signal、`mitigated_by` Task。 |
| Component | 案件内の技術要素。 | 種別（画面／FE／BE／API／バッチ／DB／テスト）、所有チーム。 | `implements` Feature、`calls` API、`covered_by` TestEvidence。 |
| TestEvidence | テスト実行・結果の一意ID。 | 種別、実施時刻、結果、環境、外部URL。 | `verifies` Feature／Component、`raises` Defect。 |
| Signal | 出所・外部ID・時刻で一意な原情報。 | source、occurred_at、received_at、permalink、可視範囲、要約、ハッシュ。 | `evidence_for` 状態／予測、`discusses` Feature／Defect。 |
| ForecastSnapshot | 案件・対象・時点で一意な予測記録。 | as_of、horizon、予測日、差分、確信度、欠損入力。 | `forecasts` Milestone／WBS、`based_on` Signal／Dependency／Review。 |

#### エッジの不変条件

すべての重要エッジは、関係そのものだけでなく、出所・確信・時間・確認状態を持つ。これがないグラフは、見栄えはよくてもPMOの判断根拠に使えない。

| エッジの属性 | ルール |
| --- | --- |
| `relation_type` | 上記の許可された型だけを使う。自由文の関係名を予測計算へ使わない。 |
| `direction` | `depends_on`、`blocks`、`impacts`、`implements`、`evidenced_by`は有向。画面とFeatureなどの相互参照が必要でも、計算上の方向を曖昧にしない。 |
| `state` | `confirmed`、`candidate`、`rejected`、`obsolete`。`candidate`は表示・レビュー対象にできるが、P0の納期計算には使わない。 |
| `provenance` | 外部ID、Signal、文書、手動登録、規則、AI候補のいずれかを必須にする。 |
| `valid_time` | 有効開始／終了と確認時刻を持つ。修正済み不具合の古い影響を、現在の影響として使わない。 |
| `tenant/project scope` | 両端のノードが同じテナントに属することを必須にする。案件横断エッジは明示的に許可された依存だけにする。 |
| `review` | 手動確定・否定には確認者・理由・時刻を残す。AIが変更したように見せない。 |

#### グラフを使う決定論的な問い合わせ

| 問い | 起点 | たどる関係 | 出力 |
| --- | --- | --- | --- |
| この不具合はどこへ影響するか | Defect | `affects` → Feature／Component → `planned_by` WBS → `contributes_to` Milestone。 | 画面、FE／BE／API、テスト、WBS、マイルストーン、未確認リンク。 |
| どの期日が遅れるか | Blocker DefectまたはWBS | `blocks`／`depends_on`の後続方向 → `contributes_to` Milestone。 | クリティカルパス上の後続、最初に悪化するマイルストーン、差分営業日数。 |
| なぜこの予測なのか | ForecastSnapshot | `based_on` → Dependency／Signal／Review。 | 予測に使った確認済み根拠、未使用の候補、欠損入力、前回からの変化。 |
| Slackの会話は何に関係するか | Signal | `discusses`候補 → Feature／Defect／WBS。 | ID一致、規則、AI候補の各根拠と、PMOによる確認操作。 |
| どの機能が根拠不足か | Feature／Milestone | 必須関係の有無・状態・鮮度を検査。 | 未紐付けWBS、未確認不具合、期限なし、古いSignal、算定不能理由。 |

#### 保存方式とスケール方針

P0でグラフDBを導入しない。既存のリレーショナルDBに、型付きのリンクテーブルと有向依存テーブルを追加し、案件単位で必要な部分グラフをクエリする。これによりテナント分離、トランザクション、既存Djangoモデルとの整合性を保つ。

| 段階 | 保存・取得方式 | 移行の判断基準 |
| --- | --- | --- |
| P0 | 既存のRDBMSに`TaskDependency`、`MilestoneTaskLink`、`WorkLink`、`Signal`を保存。再帰的な依存探索は案件・深さ・件数を制限して実行する。 | 1案件の影響探索、予測、根拠提示を十分な応答時間で完了できる。 |
| P1 | 同じ正規形から、影響範囲・根拠経路・グラフ品質指標を提供する。頻繁な問い合わせは投影・キャッシュするが、原データを正とする。 | 画面要求が増えても、エッジの出所と確認状態を失わない。 |
| P2 | 多案件横断の影響分析、GraphRAG、パス探索がRDBMSの性能・運用限界を超える場合だけ、読み取り専用のグラフ投影または専用グラフDBを評価する。 | 実測したクエリ遅延、ノード／エッジ数、運用コスト、テナント隔離を根拠に決める。 |

#### グラフ品質の指標と停止条件

| 指標 | 定義 | 悪化時の挙動 |
| --- | --- | --- |
| 依存充足率 | 着地予測対象WBSのうち、先行／後続とマイルストーンが確認済みの割合。 | 閾値未満は日数予測を低確信度または算定不能にする。 |
| 影響確認率 | 重大不具合のうち、Feature／WBS／テストのリンクが確認済みまたは否定済みの割合。 | AI候補だけで影響グラフを確定表示しない。 |
| エッジ鮮度 | 重要エッジの最終確認時刻と、対応する外部Signalの鮮度。 | 古いエッジは`要再確認`として予測根拠から除外できる。 |
| 循環依存数 | `depends_on`グラフに存在する閉路。 | 予測を停止し、循環経路と修正すべきWBSを表示する。 |
| 孤立ノード率 | Feature／Defect／WBSのうち、必要な関係を持たない割合。 | データ整備キューへ出し、根拠がない推定を避ける。 |

### グラフを含むGoal実行順

`AH-01`〜`AH-03`の後、`GE-01`〜`GE-03`を`LDF-01`〜`LDF-03`の前提として実装する。`GE-04`と`GE-05`は、ライブ着地予測画面と同時に検証する。グラフの構造・品質・根拠経路が完成する前に、GraphRAGや複数エージェントの自律ルーティングを導入しない。

### エージェント・ループ／ハーネス実装チケット

## 実機確認：タスク一覧はJira / Confluenceと比べて何が不足しているか

### 8521で確認した事実

`/tasks/` の全件表示は37件で、そのうち完了25件、ブロック中3件、進行中3件、未着手6件でした。にもかかわらず既定の並びは `案件コード → WBS` であり、一覧の先頭には完了済みの「要件定義」「基本設計」が出ます。画面の説明にある「期限の危ない順」と、実際の並びは一致していません。

- 900px高の表示で、タスク表の先頭は画面上端から **504px** の位置でした。ページヘッダー、KPI、絞り込みで半分以上を使うため、初回表示で確認できる行数が少なくなります。
- ブロック中に絞る機能自体は正しく動き、3件を表示できました。しかし利用者は「状態」セレクトを開き、「ブロック中」を選び、「絞り込む」を押す必要があります。危険な仕事へ直行する導線としては弱いです。
- 各行は、タイトルリンク、`詳細`、`編集`の3つのリンクを持ちます。タイトルと`詳細`は同じURLで、限られた横幅と視線を重複して使っています。
- `次アクション`は280pxを使う自由文ですが、実施者、期限、完了条件、関連する課題・不具合へ構造的に結び付いていません。読むことはできても、一覧上で「処理する」ことができません。
- ブロック中タスクの詳細では、進捗・遅延・担当・優先度は上部にありますが、**次アクションは15項目程度の属性の下**に置かれています。根拠メモは空でも、履歴・コメント・決定ログに進む導線がありません。

### 比較の軸

Jiraを見本としてUIを複製するのではなく、仕事を前に進めるための次の結果を取り込みます。Jiraはリスト・ボード・タイムラインなど状況に応じた表示、絞り込み、依存関係・ワークフローの追跡を提供しています。[Jira公式の機能紹介](https://www.atlassian.com/software/jira/features) [Jira公式のフィルター説明](https://support.atlassian.com/jira-core-cloud/docs/find-the-information-you-need-with-filters/)

Confluenceから取り込むべきなのは文書編集UIそのものではなく、判断の背景を仕事に近接させ、コメント・共有・通知で認識を合わせる考え方です。[Confluence公式の共同編集ガイド](https://www.atlassian.com/software/confluence/resources/guides/confluence-essentials/collaborate)

| 比較軸 | 現状 | 必要な到達点 | 初回実装の範囲 |
| --- | --- | --- | --- |
| 今日処理すべき仕事 | 完了25件も未完了と同じ一覧に並び、案件/WBS順 | ブロック中、期限超過、期限接近、担当者自身をすぐ切り替えられる | GET条件を持つクイックビュー。保存済みビューは後回し |
| 1件を開く前の判断 | 状態・優先度・次アクションを横読みする | `なぜ今対応するか`、担当、期限、次の一手が一目で分かる | 行の情報順とバッジ、主操作を整理 |
| 1件の処理 | タイトル/詳細が重複し、編集画面でしか進めにくい | 詳細で状況を確認し、必要な状態変更/関連情報に進める | タイトルを唯一の詳細入口にし、編集は補助操作へ |
| 文脈と決定 | 根拠メモが空でも次の確認先がない | 依頼、決定、根拠、関連課題を追える | まずは既存の根拠/外部原文/課題へのリンクを表示。コメント機能は別設計 |
| 一覧の見通し | 表の開始まで504px、同じ密度で37行が続く | 「優先対象」→「通常一覧」→「入力品質」の順で見る | KPIを縮めず、優先対象の短い領域をKPIの直後へ追加 |

### 品質の定義

- **当たり前品質（実装必須）**: 同じ仕事を支援する複数の既存サービスで提供され、利用者が「あるはず」と期待する機能。ここに記した項目は、提案ではなくリリース判定の必須条件として実装する。見た目を他社製品に寄せることは目的にしない。
- **魅力的品質（提案）**: VeriRAG PMO Agent が持つ、WBS・品質・課題・RAG根拠・AI実行履歴・外部同期を横断できる特性から生まれる価値。他社の画面を後追いせず、意思決定の速さと説明可能性を高める仮説として扱う。採否は利用者検証と効果測定で決める。
- **「実装必須」の完了条件**: 画面に表示するだけでは完了にしない。対象の絞り込み／詳細遷移／保存後の結果確認／空状態・権限なしの表示を受入テストで通し、該当のURLを共有して再現できることを必須とする。

### 全画面に適用する当たり前品質

1. 一覧画面は、件数・現在の条件・並び順・条件解除・詳細への一意な入口を持つ。対象が多い画面は、状態／担当／期限または相当する条件で絞り込める。
2. 重要な数値、バッジ、アラートは、クリックできるなら遷移先と条件が分かり、できないならリンクのように見せない。
3. 詳細画面は、要約と次の操作を先頭に置き、根拠・履歴・全文は後段へ置く。実行操作の直前には対象・影響・取り消し可否を表示する。

## 販売・導入・効果実証バックログ

### この節の位置付け

画面別の当たり前品質を実装しても、それだけではSIerに採用される理由になりません。この節は、機能を「誰の、どの定例業務を、どんな根拠で、どれだけ改善するか」という販売可能な単位に変換するためのものです。

ここでの市場・競合に関する記載は公開情報からの仮説です。実際の受注可能性、価格、導入期間は、対象顧客へのインタビューと有償PoCで検証するまで確定扱いにしません。

### 1. 目指す商品ポジション

> **複数案件を並行して推進するSIerのPMO／品質保証組織向けに、進捗・品質・課題・文書根拠を横断し、早期警戒と説明可能な意思決定を支援するAIエージェント基盤。**

この製品は、汎用のタスク管理、汎用RAG、あるいは人のPMOを自動置換する製品として売らない。人が最終判断を行う前提で、PMOが毎週行う「危険な案件を見つける」「根拠を集める」「報告と判断を前に進める」作業を短縮する製品として扱う。

| 売らない位置付け | 売る位置付け | なぜこの位置付けか |
| --- | --- | --- |
| Jira／Confluenceの代替 | 既存データを使うPMOの判断支援 | タスク・文書の記録基盤を置き換えるには移行・運用負担が大きい。まずは読み取り中心で価値を示す。 |
| 汎用AIチャット | 根拠と監査を伴う案件運営支援 | 生成文そのものではなく、出典・対象・採否・結果まで追えることに対価を置く。 |
| 自律的に案件を「管制」するAI | 人の判断を早めるAI副操縦士 | SIer案件の品質・契約・顧客影響を考えると、AIの自動実行より人の承認と説明責任が先に必要になる。 |
| 全社PPMの置換 | 品質・進捗リスクが高い案件群の横断早期警戒 | 原価・要員・販売管理を含む全社PPMは別の導入論点が大きい。最初の導入範囲をPMO実務に限定する。 |

### 3. 販売できる業務シナリオ

最初の商談では全機能を見せず、以下の3つから顧客の痛みが最も強い1つを選ぶ。デモもPoCも、必ず既存の実データで「入力 → 根拠 → 人の判断 → 結果確認」までを通す。

| 優先 | 業務シナリオ | 導入前の典型的な流れ | 導入後に示すべき変化 | 成功指標 |
| --- | --- | --- | --- | --- |
| 1 | 週次PMOレビュー | PMOが複数の進捗表・課題表・品質報告を集め、危険案件を人力で抽出し、報告資料を作る。 | 危険対象を理由・根拠・担当・期限つきで優先表示し、報告の下書きへつなぐ。 | 危険対象の抽出・根拠収集・報告下書きに要する時間、見落とし件数。 |
| 2 | 品質ゲート判定 | 要件、テスト、不具合、承認記録を別々に確認し、判定根拠を手作業で集める。 | 指標・未充足条件・関連証跡・未解決不具合を1つの判定パッケージへ集約する。 | 判定準備時間、差戻し回数、根拠未確認の発生率。 |
| 3 | 炎上兆候／変更判断 | 遅延・課題・不具合・変更の関係が見えず、問題が顕在化してから会議体を開く。 | 影響範囲と反証を含む早期警戒を示し、必要な判断者へ根拠付きで渡す。 | リスク検知から初回対応までの時間、期限超過の早期発見率、判断待ち滞留日数。 |

### 4. 提供パッケージ：最初は「PMO早期警戒PoC」として売る

全社展開や大規模な業務置換から始めない。対象案件を3件程度に限定した有償PoCを基本単位とし、導入後に組織展開を判断する。

| フェーズ | 期間の目安 | 顧客と合意する内容 | 成果物／判定 |
| --- | --- | --- | --- |
| 0. 適合性診断 | 1〜2週 | 対象案件、利用者、既存データ、権限、評価指標、除外範囲を確認する。 | データ可用性表、業務フロー、PoC成功条件、リスク一覧。 |
| 1. 読み取り連携・基準線計測 | 2〜3週 | 進捗・課題・不具合・品質・文書のうち、優先シナリオに必要なデータだけを取り込む。現行工数と見落としを計測する。 | データマップ、権限マップ、現状KPI、連携の失敗時手順。 |
| 2. PMO運用PoC | 4〜6週 | 週次レビューまたは品質ゲートの実運用で、早期警戒・根拠・報告下書きを使う。AI提案は人が必ず承認する。 | 週次の効果ログ、提案採否台帳、根拠確認率、運用改善点。 |
| 3. 事業化判断 | 1週 | KPI、利用継続意向、運用負荷、セキュリティ・監査の充足を共同で振り返る。 | 継続／拡張／中止の判断書、次の連携範囲、投資対効果の仮説。 |

> **PoCで約束しないこと**: 完全自動の案件判断、顧客の既存プロセス全置換、データ品質が低い状態での高精度予測、書き戻し連携の即時提供。これらを約束すると、導入失敗の原因を製品の価値と混同しやすい。

### 5. 定量KPIとROIの測り方

ROIは「AIが便利だった」というアンケートだけで証明しない。導入前の基準線と同じ対象・同じ会議体で、以下を比較する。金額換算は顧客の人件費単価と契約条件を用いて顧客自身が確認する。

| 観点 | 指標 | 定義 | 最低限の計測方法 |
| --- | --- | --- | --- |
| PMO生産性 | 定例準備時間 | データ収集開始から、レビュー可能な資料・対象一覧が揃うまでの時間。 | 3回以上の定例で、導入前後を同じ担当者・対象案件で記録する。 |
| 早期警戒 | 初回対応までの時間 | 危険兆候の発生／検知から、担当と次アクションが合意されるまでの時間。 | 課題・リスク・検知の作成時刻と、初回判断の時刻を突き合わせる。 |
| 判断品質 | 根拠確認率 | AI提案または重要判断で、出典を1件以上開いて確認した割合。 | 提案／判断ごとに根拠リンクの参照と採否理由を記録する。 |
| 品質運用 | 品質ゲート差戻し率 | 根拠不足・未解決不具合・判定条件漏れにより差戻された割合。 | 判定履歴から理由を分類し、期間比較する。 |
| 運用定着 | 週次利用継続率 | 対象ロールが、定例前に危険対象・根拠・次アクションを確認した割合。 | ログではなく、定例テンプレート上の確認記録でもよい。 |
| AI提案品質 | 採用後の有効率 | 採用した提案のうち、事後レビューで有効だったと判断された割合。 | 採否と結果を分けて記録し、「採用率」だけで評価しない。 |

### 6. 競合・代替手段との比較方針

競合の機能数を追いかけない。競合を否定するのではなく、顧客の既存基盤を前提に「何を補完し、何を置き換えないか」を明確にする。

| 顧客が比較する代替手段 | 強み／顧客の期待 | VeriRAGの勝ち筋 | 先に満たすべき当たり前品質 |

| Confluence等の文書基盤 | 共同編集、コメント、版管理、承認、文書探索。 | 文書を「保管」するだけでなく、案件の判断根拠として逆引き可能にする。 | 出典、原文遷移、権限、コメント・履歴、版・更新時点。 |

## 最優先価値提案：ライブ着地予測（Live Delivery Forecast）

### 問題：PMOが「いま」しか分からず、期日への着地を予測できない

PMOが欲しいのは、台帳上の進捗率でも、単なる「いまの実態」でもない。**2日後、1週間後、最終期日に対して、案件・機能・マイルストーンがどう着地するか。遅れる／前倒しになるなら何営業日か。その予測を、根拠と不確実性つきで即座に把握できること**である。

「いまの実態」は着地予測の入力にすぎない。開発、QA、不具合、Slack上の会話、WBS、依存関係、担当者、過去の対応速度を統合し、未来の見込みを継続的に更新することが中核価値になる。

典型例では、開発管理上は「開発中」と表示されていても、実態はQAがシステムテストを実施中であり、不具合がSlackのスレッドで議論されている。PMOは、退勤後にSlack、課題、試験結果、担当者へのヒアリングを往復して初めてこの矛盾を理解し、翌日の報告を作る。結果として「明日テストを再開できるのか」「金曜の品質ゲートに間に合うのか」「リリース日は何日ずれるのか」を答えられない。この遅れと不確実性をなくすことを、本製品の最優先価値とする。

### 提供する体験：結論ではなく「現在地・根拠・将来の着地」を一画面で示す

機能ごとの画面では、単一の状態バッジで実態を隠さない。開発、QA、障害、対応、スケジュールを並べ、互いに矛盾する情報も含めて表示する。その上で「2日後」「1週間後」「最終マイルストーン」の3時点ごとに、着地見込み・遅延／前倒し日数・確信度・根拠を示す。

| 利用者が即座に知ること | 表示する内容 | 例 |
| --- | --- | --- |
| 機能の現在地 | 開発、単体試験、結合試験、システムテスト、リリース準備の各状態。確定／推定／未確認を区別する。 | 「開発: 対応中（課題管理）／QA: システムテスト失敗（テスト結果・Slack）」。 |
| 2日後・1週間後の見込み | 各時点で継続、回復、遅延拡大、前倒しのどれが見込まれるか。予測の変化も示す。 | 「2日後: 原因切り分け完了見込み（確信度: 中）／1週間後: 総合試験開始が2営業日遅延見込み」。 |
| 最終期日の着地 | 基準日、現在の予測日、遅延／前倒し日数、影響するマイルストーン、算定可能性。 | 「本番リリース: 8/30予定 → 9/3見込み（3営業日遅延）。クリティカルパス: 結合試験」。 |
| 最新の変化 | 最終更新時刻、情報源、発言・チケット・試験結果の短い要約、原文へのリンク。 | 「16:42 QAスレッドで再現を確認。16:55 不具合 #DEF-42 を起票」。 |
| ブロッカー | 未解決不具合、ブロックされたWBS、ボール保持者、次アクション、解消期限。 | 「重大不具合1件。BE修正待ち。担当: 山田。17:00までに原因切り分け」。 |
| 影響範囲 | 画面、機能、FE、BE、API、バッチ、テストケース、関連文書、他機能への波及。 | 「受注登録画面 → 注文API → 在庫引当サービス。3テストケースが失敗」。 |
| 納期影響 | 影響するWBS、依存先、クリティカルパス、最短の解消期限、解消しない場合の遅延／前倒し見込み。 | 「8/16までに確認完了できなければ、結合試験完了が3営業日後ろ倒し」。 |
| PMOの次の行動 | 誰に何をいつ確認すべきか。情報不足なら、その不足を明示する。 | 「機能とWBSの紐付けが未確認。PMへ確認依頼を送る」。 |

### 情報の扱い：事実・推定・判断を混ぜない

Slackの会話だけで案件状態を確定してはならない。人の会話には途中経過、仮説、誤記、顧客固有の情報が含まれるためである。この機能はAIによる自動判定画面ではなく、分散した事実を集約し、矛盾と影響を人が速く判断するための画面として設計する。

| 区分 | 意味 | 表示・操作のルール |
| --- | --- | --- |
| 事実（Signal） | Slack投稿、スレッド、課題更新、不具合、テスト結果、コミット、同期結果など、時刻と出所を持つ原情報。 | 出所・時刻・原文リンクを必ず表示する。要約しても原文を消さない。 |
| 推定（Inference） | 複数の事実からAIまたはルールが導いた「QAで停止している」「影響候補はこの機能」など。 | 確信度、根拠、反証、未確認事項を表示し、事実と見た目を区別する。 |
| 判断（Decision） | PM、PMO、QA責任者などが確認して採用した状態、影響、次アクション。 | 判断者・時刻・理由・差戻しを残す。AIは無断で状態を確定／書き戻ししない。 |

### 「リアルタイム」の定義

リアルタイムを、画面を開いた瞬間の見た目ではなく、**予測に使った情報の鮮度と予測の再計算遅延**として定義する。顧客の連携方式に合わせて目標値を合意し、画面には必ず実測値を表示する。

| 項目 | 必須の扱い |
| --- | --- |
| 情報鮮度 | Slack、課題、テスト、CIなどの情報源ごとに「最終取得時刻」「最終成功」「次回取得予定／失敗理由」を示す。古い情報を現在の予測として扱わない。 |
| 予測更新 | 新しい重大Signal、WBS更新、不具合の状態変更を受けたら、対象機能・関連マイルストーンの予測を再計算する。再計算前後の差を残す。 |
| 鮮度切れ | 連携が失敗・停止・許可外で、合意した鮮度を超えた場合は「着地予測の信頼度低下」として明示する。安全側にもっともらしい予測を出し続けない。 |
| 通知 | 予測日が悪化した、確信度が大きく下がった、または重要な情報が未確認のまま期限に近づいた場合のみ通知する。通常更新で通知を乱発しない。 |

### 最小ユーザーフロー

1. Slack、課題、試験結果、既存のWBSを読み取り専用で同期する。
2. AIまたはルールが、機能名、課題番号、画面名、API名、担当者、スレッドから「関連候補」を作る。
3. PMOはライブ着地予測で、2日後・1週間後・期日のいずれかで悪化する機能、矛盾・未解決不具合・更新停止を優先順に見る。
4. 機能を開くと、工程別の現在地、根拠のタイムライン、影響範囲、2日後・1週間後・期日の着地予測、次アクションを確認する。
5. PMOまたは責任者が、関連付け・影響・次アクションを確認／修正する。確認済みの判断だけを日次・週次報告へ載せる。
6. 夕方を待たず、重要な状態変化または未確認の矛盾を通知する。定時には差分だけを自動で引き継ぐ。

| 日次引継ぎ／報告下書き | PMO | 前回確認後の変化、未確認事項、判断待ち、根拠リンクをまとめる。 | PMOが夜に情報を集め直さず、確認・編集して共有できる。 |

### データモデルと連携の方針

既存には、`WbsTask`（親子・関連タスク・計画日・クリティカルパス）、`Issue`、`Defect`、`ChangeRequest`（影響タスク・スケジュール影響日数）、`QualityMetric`、外部接続・同期履歴がある。これらは出発点として使える。一方、現在のSlack接続は通知先としては定義されているが、会話を読み取って案件実態へ結びつける取込経路はない。ここを新設する。

| 概念 | 役割 | 実装上の判断 |
| --- | --- | --- |
| Feature（機能） | PMOが把握する業務上の単位。画面・API・バッチ・テスト・WBSを束ねる。 | 既存のWBSや文書名を単に流用せず、案件配下の独立した機能台帳として持つ。最初は手動登録・CSV取込を許容する。 |
| Signal（原情報） | 会話、課題、不具合、テスト、コミット等の時刻・出所・URL・要約を持つ不変の記録。 | 外部本文を無制限に複製しない。必要最小の抜粋、外部ID、パーマリンク、取得時点、アクセス制御を持つ。 |
| Link（関連付け） | Signal、Feature、WBS、Issue、Defect、ChangeRequest、コンポーネント間のつながり。 | `確定`、`AI候補`、`否定`、`未確認`、確認者・理由・時刻を保持する。候補を確定扱いにしない。 |
| Component（技術要素） | 画面、FE、BE、API、バッチ、DB、テストケースなどの影響単位。 | 最初から完全な構成管理DBを作らない。重大機能・重大不具合に関係する要素から手動／同期で増やす。 |
| State assessment（現在地評価） | 機能の工程別状態、ブロッカー、確信度、最後に確認した人・時刻。 | Signalから再計算できる推定と、人が確定した判断を分離して保存する。 |
| Delivery forecast（着地予測） | 2日後・1週間後・最終期日の予測日、遅延／前倒し日数、確信度、予測更新時刻、根拠。 | 各時点を別の予測として保持し、前回予測との差と予測が悪化／改善した理由を示す。 |
| Schedule impact（納期影響） | ブロッカー、解消見込み、依存WBS、マイルストーンから導く遅延／前倒し見込み。 | 依存関係や解消予定が不足する場合は日数を推測しない。「算定不能」と不足データを出す。 |

### 段階的な実装ロードマップ

| 段階 | 目的 | 実装範囲 | 実装しないこと |
| --- | --- | --- | --- |
| LDF-0: データ整備 | 機能とWBS／不具合の対応を作る。 | 機能台帳、WBS・不具合・変更要求との手動関連付け、既存データの表示。 | AIによる自動分類、Slack本文の取込。 |
| LDF-1: ライブ予測の可視化 | PMOが日中に着地を確認できる。 | 2日後・1週間後・期日の予測、遅延／前倒し日数、確信度、ブロッカー、最新更新、未確認関連、根拠タイムライン、日次差分。 | 自動的な状態確定、外部への書き戻し。 |
| LDF-2: Slack読み取り連携 | 会話に埋もれた事実を候補として拾う。 | チャンネル／スレッドの読み取り、パーマリンク、取得時点、機能・課題との関連候補、権限・保持期間設定。 | DMや非許可チャンネルの取得、根拠なしの自動確定。 |
| LDF-3: 影響範囲・着地試算 | 不具合の影響と最終着地を構造的に判断できる。 | FE／BE／API／テスト／WBSの関連付け、依存関係、クリティカルパス、影響根拠つきの2日後・1週間後・期日シナリオ。 | 入力不足時のもっともらしい遅延日数の生成。 |
| LDF-4: 学習するPMO支援 | 組織固有の予測・判断パターンを再利用する。 | 予測と実績の誤差、提案採否・実結果・誤関連の学習、類似障害の処置比較、効果測定。 | 人の承認なしの自律エスカレーション。 |

### 受入条件（P0）

1. PMOは、案件を開いて30秒以内に、2日後・1週間後・最終期日のいずれで危険になる機能と、予測の確信度を区別できる。
2. 1つの重大不具合から、関係する機能、WBS、担当、次アクション、根拠となる外部レコードへ移動できる。
3. 「開発中」と「QAで不具合発生」が同時に存在する場合、状態を上書きせず矛盾として表示し、確認者を指定できる。
4. Slack等から得た内容は、原文の場所、取得時点、関連候補の確信度を表示し、利用者が否定・確定できる。
5. 遅延／前倒し日数は、依存WBS・解消見込み・期限の根拠がある場合だけ表示する。根拠がなければ算定不能と不足情報を表示する。
6. 日次報告には、前回確認後の差分、判断待ち、未確認事項、根拠リンクを含め、AIの推定だけを確定事項として載せない。

## ライブ着地予測：実装可能な詳細仕様

### 1. 予測の前提と非目標

この機能は「AIが正解の納期を当てる」機能ではない。**利用可能な事実、明示された見積り、依存関係、勤務日カレンダーから、説明・修正・検証できる着地見込みを即時に再計算する**機能である。

| 項目 | 採用する方針 | 採用しない方針 |
| --- | --- | --- |
| 予測の根拠 | WBS依存、計画日、完了実績、確認済みの解消予定、テスト再開予定、勤務日、最新Signal。 | Slackの雰囲気、進捗率だけ、根拠のないAI推測。 |
| 予測の単位 | 機能、WBS、マイルストーン、案件。各々を関連付けて遡れるようにする。 | 案件全体の単一パーセンテージだけで納期を判定する。 |
| 予測結果 | 2日後・1週間後の工程見込み、最終期日の予測日、遅延／前倒し営業日数、確信度、根拠、不足入力。 | 理由も確信度もない「順調／危険」のラベルだけ。 |
| AIの役割 | 関連候補抽出、根拠要約、矛盾・不足入力の発見、シナリオの説明。 | 期限、影響範囲、状態を無断で確定・外部へ書き戻すこと。 |
| 人の役割 | 解消見込み、関連付け、影響、回復策を確認／修正する。 | PMOが最終判断をしない自律運用。 |

### 2. 予測に必要なデータと入力責任

予測に必要なデータを「取れれば使う」扱いにしない。どの入力がなければ何を算定できないのか、誰が直すのかを明確にする。

| 入力 | 最小フィールド | 主な情報源 | 入力責任者 | 欠けた場合の扱い |
| --- | --- | --- | --- | --- |
| 機能台帳 | 機能名、案件、責任者、状態、リリース対象、関連WBS。 | 新規台帳、既存要件・バックログ。 | PM／PMO。 | 機能単位の影響と着地を出せない。WBS単位だけに限定する。 |
| WBS・依存 | 計画開始／終了、残作業、先行／後続、ラグ、クリティカルパス、親子。 | 本システム、計画ツール、CSV。 | PM。 | 後続への遅延波及と最終期日を算定不能とする。 |
| マイルストーン | 予定日、対象WBS、品質ゲート、実績日。 | 本システム、計画ツール。 | PMO／PM。 | 案件の着地日を算定不能とし、機能単位の見込みのみ出す。 |
| 不具合・課題 | 状態、重大度、検出工程、担当、原因、修正見込み、再試験予定、関連機能。 | Jira、Redmine、Azure DevOps、既存台帳。 | QA／開発リーダー。 | 「未解決の影響あり」は出せるが、解消時期・遅延日数は算定不能とする。 |
| テスト証跡 | テスト種別、対象機能、実施結果、失敗理由、不具合ID、再試験予定。 | テスト管理ツール、CI、QA台帳。 | QA。 | QA工程の進みと完了条件を推定しない。未確認として扱う。 |
| 開発活動 | PR／コミット、ビルド・チェック結果、デプロイ環境、関連課題キー。 | GitHub、GitLab、Azure DevOps、CI。 | 開発リーダー。 | 開発進行の補助根拠を失う。課題とテストを優先して予測する。 |
| 会話の事実 | チャンネル、投稿・スレッド、時刻、パーマリンク、関連候補、許可範囲。 | Slack、将来のTeams。 | チャンネル所有者／PMO。 | 会話由来の早期シグナルを使わず、台帳更新まで待つ。 |
| 勤務日・制約 | 休日、稼働日、リリース凍結、顧客確認日、外部依存の期限。 | プロジェクト設定、カレンダー。 | PMO／PM。 | 暦日を営業日として扱わず、日数予測を算定不能とする。 |

### 3. 最小の予測ロジック（P0は決定論）

P0では、機械学習による工数予測を使わない。最初に説明可能な計算を作り、予測と実績の差を十分に蓄積してから統計・AIを補助に使う。

1. **Signalを正規化する。** 不具合起票・更新、テスト失敗／成功、課題更新、確認済みのSlack会話、コミット／CI結果を時刻付きのSignalとして保存する。
2. **状態と解消見込みを確定する。** 解消見込みは、責任者が確認した日時を最優先する。未確認の会話・AI候補からは日時を作らない。
3. **WBSの予測終了日を計算する。** 完了済みは実績日、進行中は確認済みの残作業／解消見込み、未着手は計画終了日を起点にする。起点が不明なら算定不能にする。
4. **依存グラフを前方向に計算する。** 各後続タスクの予測開始日は、先行タスクの予測終了日とラグを超えられない。依存が未入力なら、遅延日数を0と見なさない。
5. **マイルストーンと期日を再計算する。** 関連する必須WBSの最大予測終了日を着地候補とし、予定日との差を営業日で遅延／前倒しとして算出する。
6. **3時点を出す。** 2日後と1週間後は「その時点でどの工程・ブロッカー・未確認が残る見込みか」、最終期日は「予測完了日と差分」を出す。単に今日から日付を足した表示にはしない。
7. **予測差分を保存する。** 前回より予測日が悪化・改善した理由、利用したSignal、未入力項目を履歴として残す。

```text
タスク予測終了日 = max(
  タスク自身の確認済み終了見込み,
  max(先行タスク予測終了日 + 依存ラグ),
  必須の未解決不具合の確認済み再試験完了見込み
)

マイルストーン予測日 = max(関連する必須タスク予測終了日)
差分営業日 = マイルストーン予測日 - マイルストーン予定日
```

上式で必要な値がないときは、数値を補完しない。`算定不能`、`未確認の先行タスク`、`再試験予定未登録`など、次に埋めるべき入力を返す。

### 4. データモデルの追加と既存モデルの拡張

`WbsTask.related_tasks` は対称的な関連であり、前後関係・ラグ・依存種別を表せない。ライブ着地予測には、明示的な依存モデルと、根拠を失わないSignalモデルが必要である。

| 概念 | 最小フィールド | 関係・ルール |
| --- | --- | --- |
| `Feature` | project、name、owner、release_target、status。 | 1機能は複数のWBS・コンポーネント・不具合・テストに結び付く。 |
| `TaskDependency` | predecessor、successor、dependency_type、lag_business_days、confirmed_by、confirmed_at。 | 少なくともFinish-to-StartをP0で扱う。循環依存を禁止する。既存の`related_tasks`は補助関係のまま残す。 |
| `MilestoneTaskLink` | milestone、task、is_required、confirmed_by。 | タスクの計画終了日が近いだけでマイルストーン必須と推定しない。 |
| `Component` | project、name、kind（画面／FE／BE／API／バッチ／DB／テスト）、owner。 | 影響範囲を技術要素で表す。P0は重大機能だけを手動登録する。 |
| `WorkLink` | from_object、to_object、relation（実装／検証／原因／影響／ブロック）、state（確定／候補／否定）、source、confirmed_by。 | Feature、WBS、Defect、Issue、ChangeRequest、Component、Signalを関連付ける。AI候補は確認されるまで予測根拠に使わない。 |
| `Signal` | source、external_id、occurred_at、received_at、permalink、summary、classification、visibility_scope、payload_hash。 | 原文を不必要に複製せず、外部ID・リンク・最小抜粋を保持する。更新・削除は追跡可能にする。 |
| `ForecastSnapshot` | as_of、horizon（2d／1w／milestone）、forecast_date、variance_business_days、confidence、method、missing_inputs、evidence_ids。 | 予測を上書きせず、時点ごとのスナップショットとして比較可能にする。 |
| `ForecastReview` | snapshot、reviewer、decision（採用／修正／却下）、reason、corrected_date。 | PMOの確認結果と、予測改善のための実績を残す。 |

### 5. 確信度のルール

確信度はAIの自己評価ではなく、入力品質の指標として計算する。表示は「高・中・低・算定不能」とし、必ず内訳を開けるようにする。

| 状態 | 最低条件 | 例 |
| --- | --- | --- |
| 高 | 必須依存とマイルストーンが確定済み、主要ブロッカーの解消見込みと再試験予定が確認済み、情報源が鮮度内。 | 重大不具合の修正・再試験予定が担当者により確認され、後続WBSと品質ゲートが紐付く。 |
| 中 | 依存と期日はあるが、解消見込みまたは一部の関連が候補／未確認。 | QA会話から影響候補はあるが、PMがWBSへの影響をまだ確認していない。 |
| 低 | 古い情報、矛盾した状態、未確認の重大ブロッカー、未登録の先行タスクがある。 | Slackでは再現済みだが、不具合台帳未起票で担当・期限が不明。 |
| 算定不能 | 期日、依存、対象WBS、解消見込みのいずれかが欠落し、日数計算の前提がない。 | 「機能は分かるが、リリース対象とマイルストーンが未紐付け」。 |

### 6. 外部システム連携の全体アーキテクチャ

各システムのデータを直接WBSや不具合へ上書きしない。すべてをいったん原情報である`InboundEvent`／`Signal`として受け、正規化・関連付け・予測再計算の順で処理する。これにより、同期の失敗、重複、外部側の訂正、AI候補の誤りを追跡できる。

```text
外部システム
  └ Webhook または定期取得
       └ 署名検証・認可・冪等受付（InboundEvent）
            └ 正規化（Signal）
                 └ 関連付け：ID一致 → 手動確定 → 規則 → AI候補
                      └ 予測再計算（Feature / WBS / Milestone）
                           ├ ライブ着地予測・影響範囲ビュー
                           ├ 予測悪化時の通知
                           └ 日次／週次報告の下書き
```

| 処理段階 | 実装の責務 | 必須の安全策 |
| --- | --- | --- |
| 接続設定 | テナント・案件・情報源・読み書き方向・許可範囲・資格情報参照名を登録する。 | 資格情報の値はDB・ログ・画面に保存しない。P0は外部→内部の読み取り専用。 |
| 受付 | Webhookを検証してすぐ永続化する。Webhookがない製品は増分ポーリングする。 | 署名または送信元を検証し、外部イベントID／ハッシュで重複を除く。失敗を握りつぶさない。 |
| 正規化 | 製品固有のペイロードをSignal、課題、不具合、テスト、開発活動などへ変換する。 | 原文・時刻・URL・権限範囲を失わない。外部の自由文をそのまま予測値に使わない。 |
| 関連付け | 既知ID、明示リンク、命名規則、AI候補の順にFeature／WBS等と結ぶ。 | AI候補は人が確定するまで予測の決定根拠にしない。否定済み候補を再提案しない。 |
| 再計算 | 影響を受けるFeature、後続WBS、マイルストーンだけを再計算する。 | 根拠・入力不足・前回との差をSnapshotに保存する。 |
| 表示・通知 | 予測の悪化、確信度低下、未確認の期限接近だけを利用者へ出す。 | 予測の数字だけを通知しない。対象・理由・根拠・確認先を含める。 |

### 7. 連携先ごとの接続方法と使うデータ

| 優先 | 連携先 | 予測に使うデータ | 接続方法 | P0の範囲／注意点 |
| --- | --- | --- | --- | --- |
| 1 | Slack | チャンネル投稿、スレッド、投稿時刻、パーマリンク、課題キー／機能名、明示された見込み・ブロッカー。 | 許可済みプロジェクトチャンネルに限定してEvents APIで受信し、必要時に会話APIでスレッドを取得する。 | DM、非許可チャンネル、全文の無期限複製は対象外。会話はSignal候補であり、状態・期日の自動確定には使わない。 |

### 8. 接続設定から稼働開始までの手順

1. **接続を作成する。** 管理者が連携先、テナント、案件、動作モード、読み書き方向を選ぶ。P0では「外部→内部／読み取り専用」に固定する。
2. **最小権限で認可する。** Slackは対象チャンネル、Jira／Redmineは対象プロジェクト、Confluenceは対象スペース、Gitは対象リポジトリだけを選ぶ。資格情報は環境変数または秘密情報ストアの参照名だけを保存する。
3. **対象範囲をプレビューする。** 取り込まれる件数、最古／最新時刻、見えるユーザー、本文保存の有無を表示し、管理者が確定する。
4. **フィールド対応を確認する。** 外部の状態・優先度・担当・期限・不具合種別・課題キーを、内部の正規値へ対応付ける。未対応値は既定値へ黙って寄せず、警告として扱う。
5. **初回ベースラインを取り込む。** 直近の合意期間だけを取得し、重複・欠損・権限エラー・時刻ずれを検査する。過去全履歴の無条件取込は行わない。
6. **機能／WBSとの関連を確認する。** 正確なID一致を先に適用し、名称一致・AI候補はPMOが確認する。確認率が基準未満なら着地予測を有効化しない。
7. **予測を有効化する。** 鮮度目標、再計算条件、通知先、日次引継ぎ時刻を案件ごとに設定する。
8. **監視・定期照合する。** Webhookの受信失敗、同期遅延、スキーマ変更、未対応の状態値、関連未確認を接続監視へ出す。Webhookだけに依存せず、定期的に差分照合する。

### 9. 外部データの関連付け優先順位

誤った紐付けが一度予測へ入ると、もっともらしい誤報が連鎖する。関連付けは次の順に厳格に行う。

1. **明示的ID一致**: 外部課題キー、テストケースID、PRの課題キー、Slack投稿内の正式ID、外部URL。自動確定できる。
2. **人が作った確定リンク**: PMO／PM／QAが登録・確認した機能、WBS、コンポーネントのリンク。自動確定できる。
3. **設定済み規則**: ブランチ名、ラベル、コンポーネント名、チャンネルと案件の固定対応。規則の版と適用理由を記録する。
4. **AI候補**: 類似名称、文脈、RAG結果から提案する。根拠と確信度を表示するが、予測の確定根拠には使わない。
5. **未関連**: どこにも結び付かないSignal。削除せず、PMOが後で関連付け・除外できる状態で残す。

### 11. 品質・安全性・監査の受入条件

1. 外部イベントは、同じIDまたは同じ内容の再送でも二重にSignalや通知を作らない。
2. Slack等の連携を停止・失敗した場合、最後の取得時刻と予測への影響を表示し、古いデータを現在の事実として表示しない。
3. テナント・案件・チャンネル・プロジェクトの権限外データは、検索、RAG、予測、報告のすべてで参照されない。
4. 外部自由文、AI要約、AI候補リンクは、確定した課題・不具合・納期情報と視覚的に区別される。
5. 予測に使った依存・Signal・確認済み見込み・勤務日を、任意のSnapshotから追跡できる。
6. 外部側の削除・訂正・権限変更があった場合、内部のSignalを静かに残し続けず、表示可否・根拠の有効性・予測への影響を再評価する。
7. 各連携先で、初回同期、増分同期、Webhook受信、Webhook再送、失敗、認可失効、スキーマ未対応値、権限なしを自動テストする。
8. 予測エンジンは、依存なし、直列依存、分岐・合流、クリティカルパス、循環依存、休日、前倒し、算定不能を例示データで検証する。

### 13. PoCの成功判定

PoCでは、3案件のうち少なくとも1案件で「重大不具合の発生 → 影響機能・WBSの確認 → 2日後・1週間後・期日の着地更新 → PMOの報告」を実データで完走する。以下を満たした時だけ、ライブ着地予測が売り物として成立したと判断する。

- PMOが従来より早く、予測悪化を根拠付きで把握できる。
- 予測の算定不能・低確信度が隠されず、入力改善の行動につながる。
- 実績との比較で、遅延／前倒しの予測誤差と、その理由を説明できる。
- Slack等の会話を取り込んでも、権限・機密・監査の要件を満たす。
- PMO、PM、QAのいずれかが、日次または週次の実業務で継続利用する。
