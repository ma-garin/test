# 検証事業モデル 設計案（レビュー用・第2版）

ソフトウェア第三者検証の受託事業向けに `apps/performance` を拡張する案。
**未実装。土台（モデル・取込の枠組み）までを Claude が用意し、本実装は Codex（社内環境）が行う。**

対応するモック: [検証事業 計数ダッシュボード](https://claude.ai/code/artifact/3586562c-7808-4ced-b406-86264d72a0e8)

---

## 0. 第1版からの訂正

第1版は「単価 × 稼働を入力して売上を計算する」設計だったが、**実態と違っていた**。

| 論点 | 第1版（誤り） | 第2版（本書） |
|---|---|---|
| システムの役割 | 売上を計算する | **経理の確定値を受け取って見せる** |
| 計数の入手 | 画面から手入力 | **月次CSV（第4営業日）** |
| 単価・原価率 | モデルに持つ | **持たない**（社外秘。9職能別の係数は社内に閉じる） |
| 更新タイミング | 随時 | **月1回のみ**。それ以外は数字が動かない |

この違いは設計の骨格を変える。**このシステムは計算機ではなく台帳である。**

---

## 1. 設計の中心に置くこと

### 1-1. 数字は「いつ時点の確定値か」が常に分かること

締め日にしか数字が動かないため、利用者は「この数字は最新か」を判断できないと
意思決定に使えない。**取込のたびに「どの月度まで確定したか」を記録し、画面に出す。**

未確定の月は行を出さず、「実績未着」と次回反映日を示す。
空欄で並べると「実績0」なのか「まだ届いていない」のかを区別できない。

### 1-2. 社外秘の値をシステムに持たせない

単価・原価率・職能別係数はモデルに置かない。CSVに含まれる粒度だけを扱う。
Codex 側で列を差し替えられるよう、**CSVの列定義はコードに埋めず設定へ外出しする。**

### 1-3. 列定義を知らなくても土台が組めること

Claude は実列名を知らない。よって取込は次の2層に分ける。

```
[CSVファイル] → 列マッピング（設定） → 正規化された行 → モデルへ保存
                 ↑ Codex が差し替える     ↑ ここから先は列名に依存しない
```

## 2. 追加するモデル

```text
Tenant
├── OrgUnit（既存：部 → 課）
│   └── OrgMember（既存：要員）
│
├── Project【新規】検証案件
│   └── contract_type: 準委任 / 請負 / 派遣
│
├── Assignment【新規】アサイン（誰が・どの案件に・いつからいつまで）
│
├── MonthlyFigure【新規】月次の確定計数（経理CSV由来）
│
└── ClosingPeriod【新規】締めの記録（どの月度まで確定したか）
```

### 2-1. `Project`（検証案件）

| フィールド | 型 | 意味 |
|---|---|---|
| `tenant` | FK | テナント |
| `code` | Slug | 案件コード（テナント内で一意） |
| `name` | Char | 案件名 |
| `org_unit` | FK | 売上を計上する組織 |
| `contract_type` | Char(choices) | `entrustment`（準委任）/ `contract`（請負）/ `dispatch`（派遣） |
| `client_name` | Char | 顧客名 |
| `started_on` / `ended_on` | Date(null) | 案件期間 |
| `status` | Char(choices) | `active` / `closed` |

`OrgUnit` との違い: `OrgUnit` は**組織階層**（誰の配下か）、`Project` は**受注案件**（誰に売るか）。
1つの課が複数案件を持ち、1人が複数案件を掛け持ちするため、階層とは別に持つ。

### 2-2. `Assignment`（アサイン）

| フィールド | 型 | 意味 |
|---|---|---|
| `member` | FK → OrgMember | 誰が |
| `project` | FK → Project | どの案件に |
| `started_on` | Date | いつから |
| `ended_on` | Date(null) | いつまで（継続中は null） |

**制約**: 同一 `member` × `project` で期間が重ならないこと（アプリ層で検証）。

待機はアサインが無い状態として表現する。**待機用のダミー案件は作らない。**

### 2-3. `MonthlyFigure`（月次の確定計数）

経理CSVから取り込む本体。**このシステムはここへ書き込むだけで、計算しない。**

| フィールド | 型 | 意味 |
|---|---|---|
| `tenant` | FK | テナント |
| `fiscal_year` | FK | 年度 |
| `month` | Date | 対象月（月初日） |
| `scope_type` | Char(choices) | `org` / `project` / `member` — どの粒度の行か |
| `org_unit` | FK(null) | 組織（`scope_type=org` のとき必須） |
| `project` | FK(null) | 案件（`scope_type=project` のとき必須） |
| `member` | FK(null) | 要員（`scope_type=member` のとき必須） |
| `revenue` | Decimal | 売上 |
| `cost` | Decimal | 原価 |
| `gross_profit` | Decimal | 粗利 |
| `operating_profit` | Decimal | 利益 |
| `workload` | Decimal(5,2) null | 稼働（人月）。CSVに含まれない場合は null |
| `closing` | FK → ClosingPeriod | どの締めで入った値か |
| `source_row` | JSON | 取込元の行（差分調査用） |

**`scope_type` を持たせる理由**: CSV の粒度を外から決め打ちしないため。
組織単位でも案件単位でも要員単位でも、同じテーブルで受けられる形にしておく。
Codex は実際の粒度に合わせて `scope_type` を1つに固定すればよい
（3通り受けられる形から1つへ絞るのは容易だが、逆は作り直しになる）。

**制約**: `closing` + `scope_type` + 各FK + `month` で一意。

**`workload` が null のとき**: 稼働率を「0%」と表示しない。「—（未取得）」とする。

### 2-4. `ClosingPeriod`（締めの記録）

| フィールド | 型 | 意味 |
|---|---|---|
| `tenant` | FK | テナント |
| `closed_month` | Date | どの月度の締めか（月初日） |
| `imported_at` | DateTime | 取込日時 |
| `imported_by` | FK(null) | 取込実行者 |
| `filename` | Char | 取込ファイル名 |
| `row_count` | Int | 取込行数 |
| `status` | Char(choices) | `applied` / `superseded`（再取込で置き換えられた） |

**再取込への対応**: 同じ月度を取り込み直したとき、旧 `ClosingPeriod` を `superseded` にし、
新しい行を有効とする。**旧データを消さない。**経理から訂正版が来たとき、
何がどう変わったかを追えなくなるため。

集計は `status=applied` の `ClosingPeriod` に紐づく行だけを見る。

### 2-5. `FiscalYear` への四半期

四半期は期首月から導出する。フィールドは足さない。

```python
@property
def quarters(self) -> list[Quarter]:
    """期首から3か月ずつ4本。3月決算なら 1Q=4-6月。"""
```

決算期変更で4本に割り切れない年度では、**四半期表示を出さない**。
無理に4等分すると、どの月がどの期か誰も説明できなくなる。

## 3. CSV取込の枠組み（Codex が差し替える部分）

### 3-1. 列マッピングを設定へ外出しする

```python
# apps/performance/csv_schema.py（Claude が用意する骨格）

@dataclass(frozen=True)
class ColumnMap:
    """CSVの列名と、正規化後のフィールド名の対応。

    実際の列名は社外秘のため、既定値はダミー。
    Codex が settings または環境変数で差し替える。
    """
    org_code: str
    month: str
    revenue: str
    cost: str
    gross_profit: str
    operating_profit: str
    workload: str | None = None   # 稼働列が無いCSVもある
    project_code: str | None = None
    employee_code: str | None = None
```

差し替え方（Codex 側）:

```python
# config/settings/production.py などで
PERFORMANCE_CSV_COLUMNS = {
    "org_code": "＜実際の列名＞",
    "month": "＜実際の列名＞",
    # ...
}
```

### 3-2. 取込の流れ

```
1. ファイルを読む（UTF-8 / CP932 の両対応。既存の csv_io.decode を再利用）
2. ColumnMap で列を引き当てる → 見つからない必須列があれば、1行も入れずに突き返す
3. 正規化した行を作る（ここから先は列名に依存しない）
4. 検証（組織コードの存在、月の妥当性、数値として読めるか）
5. ClosingPeriod を作り、MonthlyFigure を一括作成
6. 同じ月度の旧 ClosingPeriod があれば superseded にする
```

**1行でもエラーがあれば何も取り込まない**（既存の CSV 取込と同じ方針）。
経理の確定値を半端に入れると、どこまで正しいか誰も判断できなくなる。

### 3-3. Claude が用意する範囲 / Codex が埋める範囲

| 項目 | Claude | Codex |
|---|---|---|
| モデル定義・マイグレーション | ○ | — |
| `ColumnMap` の構造 | ○ | 実際の列名を設定 |
| 取込の流れ（検証・保存・再取込） | ○ | — |
| 集計サービス（四半期・契約形態別・稼働率） | ○ | — |
| 画面（ダッシュボード・要員別・案件別） | ○ | — |
| ダミーデータ投入コマンド | ○ | 実データでの検証 |
| 原価率・職能別係数 | **触れない** | ○ |

## 4. 既存モデルをどうするか

### 4-1. `PlanFigure` / `PlanVersion` は残す

計画（期初・期中変更）は引き続きこのシステムで持つ。経理から来るのは実績だけ。

### 4-2. `ActualFigure` は `MonthlyFigure` へ置き換える

`ActualFigure` は「画面から手入力する実績」を前提にしていた。
実績が経理CSV由来になったため役割が重複する。**`MonthlyFigure` に一本化する。**

現時点では体験用データしかないため、移行スクリプトは不要。テーブルごと置き換える。

### 4-3. 集計ルール

```
組織の計数 = その組織に紐づく MonthlyFigure の合計 + 配下組織の合計
```

`scope_type` が `member` や `project` の行は、**所属組織へ集約してから足す**。
同じ売上を組織行と要員行の両方で持つCSVが来た場合、二重計上になる。
これを防ぐため、**1つの `ClosingPeriod` 内では `scope_type` を1種類に限定する**
（混在したCSVは取込時に弾く）。

## 6. 仮置きしていること（Codex 側で確定する）

CSV の実仕様は社外秘のため、本書では次を**仮置き**した。
いずれも Codex が社内で確定させる前提であり、外から確認しない。

| 仮置きしたこと | 本書での扱い | 違った場合に直す場所 |
|---|---|---|
| 稼働（人月）が計数CSVに含まれる | `MonthlyFigure.workload` に持つ（null 可） | 別系統から来るなら取込を2本にし、突合のずれを画面へ出す |
| CSVの粒度 | `scope_type` で組織／案件／要員の3通りを受けられる形にした | どれか1つに固定してよい。制約を強める方向なので後から絞れる |
| 経理からの訂正版がありうる | `ClosingPeriod.status = superseded` で旧データを残す | 訂正が無いなら使わないだけ。持っていて困る仕組みではない |
| 請負の要員別売上は投入工数で按分 | 按分値であることを画面に明記 | 要員別売上を出さない判断もありうる。集計側の分岐で対応できる |

**設計方針**: 仮置きはすべて「後から絞れる」側へ倒してある。
3粒度を受けられる形にしておけば1粒度へ制限するのは容易だが、逆は作り直しになる。
