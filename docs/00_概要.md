# 00 概要

## 解く問題

システム開発では後から CUD（追加・変更・削除）が発生する。そのたびに QA は
影響範囲確認 → テスト計画・分析・設計・詳細設計・ケース実装・実行・レポート → 既存リグレッションの該当ケースを失効させ新ケースを組み込む、を人手で回している。
qa-sentinel はこの一連を、複数トリガーから自律的に回す。人が入るのは「期待結果を決められない仕様」と「承認」の 2 点だけ。

## トリガー（プロジェクトごとに切り替え）

| # | トリガー | 入力 | 初回範囲 |
|---|---|---|---|
| ④ | 自然言語 | CLI / Web の指示文 | S2 |
| ③ | PR | 本文の関係 ID 欄 ＋ diff | S3 |
| ① | 仕様書投入 | ドキュメントのディレクトリ差分 | S4 |
| ② | JIRA / Confluence / Redmine | REST ポーリング（`direct` / `relay`） | S4 |

## 守る制約（2026-09-21 インシデントより）

1 時間ごとの自己チェックインが週間上限を月曜に使い切った。原因は「内容に関係なく、ターンを 1 つ増やすだけで累積コンテキスト全体を再読する」こと。

- **LLM を起こすのはイベントがあるときだけ。** 監視は LLM を使わない決定論的コードが行う。
- 1 イベント = 1 セッション。**session budget（金額上限）を必ず設定**する。
- 人の承認待ちはセッションを**終了**し、承認が新しいイベントとして `continue` で再開する。「定期的に自分を起こして確認する」設計を持たない。
- 台帳（`tasks/<id>.json`）が真実源。CLI と Web は台帳を読むだけで、セッションに問い合わせない。
