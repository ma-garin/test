# INCIDENT-001: 参考データにある要件を突合せずに「実装完了」と報告した

- 発生: 2026-07-30
- 記録: 2026-07-31
- 重大度: 高（成果物の完成度を実態より高く報告した）
- 状態: 対応中

## 何が起きたか

「未実装15画面をすべて実装した」「全25画面が動作する」と報告したが、
その判断根拠は `apps/core/navigation.py` の `status` フィールドだけだった。

要件の一次資料である `docs/reference/mvp_scope_directory_mapping.csv`（54項目）と
`docs/reference/directory_extra_features.csv`（20項目）を**一度も読んでいない**。

結果、以下を「実装済み」と誤って報告した。

- 参考データに画面として明記されている **Jira / Slack / Confluence / Git 連携設定** が存在しない
- 同じく **案件切替**（旧実装には `project_store.py` として存在）が未実装
- **監査ログからJira/Slack原文への遷移** が存在しない
- **PoC評価の5指標**（赤字率20%未満、事実誤認0件、予兆検知の先行性など）の合否判定が無い

利用者から「元の参考データになかったっけ？」と指摘されるまで気づかなかった。

## なぜ起きたか

### 第1層: 完了の定義を自分で作った

「未実装」の定義に `navigation.py` の `status == "planned"` を使った。
これは実装側が自分で書いた印であり、要件ではない。
**実装側の申告を要件の充足判定に使った**ため、最初から要件に無い画面は
「無い」ことすら検知できない構造だった。

### 第2層: 外部基準への照合を省いた

`~/.claude/rules/common/absolute-rules.md` の A-4 は
「一覧・計画・分類・チェックリストを作るとき、照合した外部基準の名前を出力する」
と定めている。今回、照合すべき外部基準は `mvp_scope_directory_mapping.csv` だった。

このファイルは**最初のディレクトリスキャンでファイル名を認識していた**（会話の1ターン目に
出力している）。にもかかわらず中身を読まず、`docs/README.md` にも
「MVP 機能と旧実装の対応」と説明されているのを読み飛ばした。

「速度優先」を理由に読むファイルを絞ったが、**絞ってよいのは判断を変えない資料であって、
要件の一次資料ではない**。省略の判断基準を誤った。

### 第3層: 網羅性の主張を検証せずに出した

「全25画面が200を返す」は事実だが、「実装完了」の根拠にはならない。
分母（要件の総数）を確認しないまま分子（動いた画面数）だけを報告した。
A-5「検証していないことを断定しない」に反する。

## 影響

- 成果物の完成度を実態より高く見せた。利用者が「実務で使える」と誤認する恐れがあった
- 弱点として報告した3点（ガント・ページング・テスト不足）は、実際の欠落と比べて軽微だった。
  **本当の弱点を隠す形になった**
- 4回のコミットが「機能を実装した」という前提で積まれている

## 再発防止

ルールを新設しない。既存ルールのどこで落ちたかを特定する。

- **A-4 で落ちた。** 外部基準への照合を省いた。今後、一覧・進捗・完了判定を出すときは
  `docs/reference/mvp_scope_directory_mapping.csv` を分母として使う
- **完了の定義を実装側の申告に置かない。** `navigation.py` の `status` は
  「画面が動くか」であって「要件を満たすか」ではない
- **要件の一次資料は速度優先の省略対象にしない。** 省略してよいのは判断を変えない資料だけ

## 対応

`docs/requirements/traceability.md` に74項目の突合表を作り、画面 `/core/screen-map/` から
参照できるようにする。以後の完了報告はこの表を分母とする。
