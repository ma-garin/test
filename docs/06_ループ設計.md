# 06 ループ設計（ループエンジニアリング）

エージェントの「自走」は、複数のループの組み合わせでできている。ループごとに **終了条件・上限・記録・脱出先** を決めないと、止まらない／同じ失敗を繰り返す／お金だけ減る。qa-sentinel に存在するループを全部列挙し、それぞれの設計を固定する。

## 1. ループの一覧

| # | ループ | 回るもの | 終了条件（成功） | 上限（失敗の脱出） | 脱出先 | 記録 |
|---|---|---|---|---|---|---|
| L1 | 監視 | ポーラー（LLM なし） | 変化を検知 → イベント化 | なし（無限。ただし LLM を起こさない） | イベントがあれば L2 | `tasks/.tracker-<p>.json`（polls・events・sessions_started） |
| L2 | タスク（段の列） | 段 test-plan → … → regression-swap | 全段 done → 承認待ち | 予算上限（セッション budget） | `stopped` → 人 | 台帳 history |
| L3 | 段の中（生成→検証） | 下書き → `run_gate` → 直し | gate exit 0 | 同一段 **2 周**（`MAX_ROUNDS_PER_PHASE`） | `blocked` → 人 | 台帳 evidence（gate 名・exit code） |
| L4 | 実行→修整（テスト実行段） | 実行 → FAIL を ODC 分類 → 最小差分で修整 → 再実行 | Critical/High 残ゼロ | 同一欠陥 **2 周**。修整はテスト資産のみ（製品コードは提案） | `blocked`（原因が設計／製品側） | odc_analysis.md、修整差分 |
| L5 | 差し戻し（人 ↔ AI） | 人が reject → AI が同じ段をやり直す | 人が ok | 同一段の reject **3 回**で `stopped` | 人（進め方の見直し） | decisions（reject の理由） |
| L6 | 質問→回答 | AI が確認待ち → 人が answer → 続き | 回答が来る | 同一タスクの確認待ち **5 件**で `stopped` | 人（仕様の欠落が多すぎる） | decisions（answer） |
| L7 | 再開 | 人の操作（ok / results / answer）→ 新セッション | 次の段へ進む | セッション数 **10 / タスク** | `stopped` | history のセッション ID 列 |

L1 だけが常時回る。L2〜L7 は **イベントが来たときだけ** 回り、止まるときは必ずセッションを終了する（待ち状態でトークンを使わない）。

## 2. 技法（各ループに適用する 8 つ）

| 技法 | 内容 | どこで使う |
|---|---|---|
| 機械判定で閉じる | ループの終了条件は exit code・件数・差分の有無で判定し、LLM に「終わったか」を聞かない | L3・L4（`run_gate`）、L2（予算） |
| 上限を数で持つ | 周回数・件数・セッション数・金額の 4 種を必ず数値で持ち、超えたら `stopped` と理由を残す | 全ループ |
| 生成と批評を分ける | 下書きした本人に合否を判定させない。判定はスクリプトか別エージェント（レビュー役） | L3（gate）、L5（人）、開発の段取り（Opus レビュー） |
| 最小差分 | 修整は「観測した失敗を狙った最小の変更」。広い書き換えはやり直しの原因になる | L4 |
| 逆適用で確かめる | 修整後、差分を逆適用して赤に戻ることを確認（直したつもりを防ぐ） | L4 |
| 状態は外に置く | ループの進み具合はメモリではなく台帳（ファイル）に書く。プロセスが落ちても同じ段から再開できる | L2・L7 |
| 冪等にする | 同じイベント・同じ操作を 2 回受けても結果が変わらない（イベント ID で重複を捨てる、失効の印は上書き可） | L1・L2・T03 の swap |
| 止まる理由を人の言葉で | `stopped` / `blocked` には「何が足りないか」「次に人が何をするか」を 1 行で | 全ループ |

## 3. 止まる条件の優先順位

同時に複数の条件に当たったときは、上から順に判定する。

1. 予算超過（`budget_reached`） → `stopped`。再開は人が予算を上げてから
2. 製品コードの不具合が原因（修整の対象外） → `blocked`。直し方の案を出して人へ
3. 仕様に無いことを決める必要がある → `blocked`（確認待ち）
4. 同一段の周回上限 → `blocked`
5. 差し戻し・確認待ちの回数上限 → `stopped`（進め方の見直し）

## 4. 実装への対応

| 設定値 | 既定 | 置き場所 |
|---|---|---|
| `MAX_ROUNDS_PER_PHASE` | 2 | `qa_sentinel/core/state.py` |
| `MAX_REJECTS_PER_PHASE` | 3 | 同上 |
| `MAX_QUESTIONS_PER_TASK` | 5 | 同上 |
| `MAX_SESSIONS_PER_TASK` | 10 | 同上 |
| `budget_usd` | 5.0 | `projects/<p>/config.toml` と開始時の 4 問 |

- L3/L4 の周回は Managed Agents のセッション内（system prompt の「同一欠陥は 2 周まで」）。ホストは gate の結果だけを見る
- L5〜L7 の上限は `core/orchestrator.py` が台帳の decisions・history を数えて判定する（Codex 指示書 T07 として切り出す）
- L1 は `triggers/tracker.py`（T06）。LLM を呼ぶ経路を持たない

## 5. 開発の段取りにも同じ形を使う

qa-sentinel 自体を作る作業も同じループ設計で回した（`.claude/skills/fanout-review-fix/`）:
Sonnet が並列で下書き → Opus が別役で批評（1 周・上限 12 件） → 下書きした本人が直す → Haiku が git。生成と批評の分離・上限・記録（PR 本文）は上の技法そのもの。
