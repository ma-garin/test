# ADR-0001: Django のモジュラーモノリスを採用する

- 状態: 採用
- 日付: 2026-07-30

## 背景

現行は Streamlit の単一ファイル（約 18,700 行）。UI・業務ロジック・検索・永続化が
同じ関数の中に混ざっており、変更の影響範囲が読めない。再構築ブリーフは
Web UI / 業務API / AI・RAGサービス / 非同期ジョブ / データストア / 認証認可 の
責務分割を求めている。

## 決定

Django のモジュラーモノリスにする。業務ドメインごとに Django アプリを分け、
アプリ内は models / selectors / services / views に分ける。
最初からマイクロサービスへは分けない。

## 理由

- 認証・認可・管理画面・マイグレーション・ORM が標準で揃っており、
  再構築で作るべきものが業務ロジックに集中する
- アプリ境界とサービス層を先に引いておけば、必要になった単位で切り出せる
- チーム規模とデプロイ先が未確定の段階で分散システムにすると、
  運用コストが機能開発を圧迫する

## 影響

- アプリ間の依存は一方向に保つ（`docs/architecture.md` の依存表）
- ビューから ORM を直接触らず、参照は selectors、更新は services を通す
- 将来 API が必要になったら、同じ services の上に DRF を載せる

## 検討した代替案

- **FastAPI + SPA**: API と UI を分けられるが、認証・管理画面・ORM を自前で組む
  必要があり、初期コストが大きい
- **Streamlit のまま分割**: 画面と状態管理の制約（セッション依存、URL 設計不可）が
  残り、ブリーフの責務分割を満たせない
