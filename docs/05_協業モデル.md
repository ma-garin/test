# 05 協業モデル — AI が下書き、人が直して確定

2026-09-28 の判断。「AI か人か」ではなく、各段で **AI が下書きし、人が直して確定する** を基本形にする。
不安（根拠が見えない・勝手に書き換える・コストが読めない・責任が曖昧）は全部あるので、安全策 4 つを常時有効にする。

## 1. 各段の役割

| 役割 | 誰 | 内容 |
|---|---|---|
| 下書き（drafter） | AI または 人 | 段の成果物を作る。AI の下書きには **根拠**（仕様の節・スクリプトの exit code・実行ログのパス）を必ず付ける |
| 確定（confirmer） | 人（名前つき） | 下書きを直して OK を押す。押すまで次の段へ進まない。差し戻しは同じ段を AI がやり直す |
| 回答（answer） | 人 | 下書き中に決められないことが出たとき（確認待ち） |

段の出口で止まる。段の途中（ケース単位）では止まらない。

## 2. 安全策（常時有効）

| 不安 | 安全策 | どこで効く |
|---|---|---|
| 何を根拠に決めたか見えない | 成果物ごとに `evidence`（仕様の節 ID・gate 名と exit code・ログのパス）を台帳に残す。根拠の無い下書きは確定画面に出さない | `PhaseResult.evidence` → 台帳 |
| 勝手にコードやケースを書き換える | AI は **作業ブランチ**（`qa-sentinel/<task>`）にだけ書く。人の確定で本線へ。製品コードは **原因と直し方の案** まで（修整しない） | ランタイムの書き込み先・system prompt |
| コストが読めない | 段ごとの予算と実績を CLI/Web に常時表示。上限で止まる | `session.budget`・台帳 |
| 責任の所在 | 確定・回答・承認は必ず人の名前で `decisions[]` に記録。AI は下書きの作成者としてしか残らない | `Task.decisions` |

## 3. タスク開始時の 4 問（毎回聞く。既定値は前回の選択）

```
$ qa-sentinel run --project library-loan --nl "貸出上限を 3 冊に"
? どの段まで AI が下書きしますか        › [計画〜差し替え（全部）] / 計画〜ケース実装 / 計画〜ケース設計 / 差し替えだけ
? どの段の出口で止まって確認しますか    › [ケース設計, 差し替え] （複数可。全部＝各段承認）
? だれが確認しますか                     › [yuki]
? このタスクの予算は                     › [$5.00]
```

非対話（CI・relay ポーラー）では `--mode <preset>` か `--draft-until/--stop-at/--reviewer/--budget` で渡す。

## 4. プリセット（4 問の組み合わせに名前を付けたもの）

| 名前 | AI が下書きする段 | 止まる出口 | 向く場面 |
|---|---|---|---|
| M1 全自動 | 全部 | 差し替え | サンプル・PoC |
| M2 実装まで AI、実行は人 | 計画〜ケース実装、不具合分析〜差し替え | ケース設計・（実行は人が下書き）・差し替え | 実行環境がクラウドから届かない現場 |
| M3 各段承認 | 全部 | 全段 | 監査要件が強い案件 |
| M4 設計まで AI | 計画〜ケース設計 | ケース設計 | 実装以降を人が持つチーム |
| M5 実行と分析だけ AI | 実行〜差し替え | 差し替え | 自動化エンジニアが書いたスクリプトを回す |
| M6 差し替えだけ AI | 差し替え | 差し替え | 導入の最初の一歩 |
| M7 レビュー専任 | なし（人が全段下書き。AI は各段でレビュー） | 全段 | AI に作らせたくないチーム |
| M8 ペア | 全部 | 全段（ケース単位の介入は持たない） | 人が常に横で見る |

## 5. 台帳への追加

```json
{
  "mode": "M2",
  "plan": {"draft_until": "test-implementation", "stop_at": ["test-design", "regression-swap"], "reviewer": "yuki", "budget_usd": 5.0},
  "branch": "qa-sentinel/T-0042",
  "phase": "test-design", "status": "review",
  "evidence": {"test-design": ["spec.md#4", "cases: exit 0"]},
  "decisions": [{"at": "...", "by": "yuki", "kind": "confirm", "phase": "test-design", "note": "ST-014 の期待結果を修正"}]
}
```

状態: `queued → running → (review | handoff | blocked | stopped) → … → paused → done`
- `review`: AI の下書き完了、人の確定待ち（セッション終了）
- `handoff`: この段は人が下書き。人の入力待ち（セッション終了）
- `blocked`: 確認待ち（回答待ち）
- `paused`: 全段完了、最終承認待ち

## 6. CLI

| コマンド | 用途 |
|---|---|
| `run` | 4 問 → 台帳作成 → セッション起動 |
| `ok <task> --by <name> -m "<直した点>"` | AI の下書きを確定して次の段へ（新セッション） |
| `reject <task> --by <name> -m "<理由>"` | 差し戻し。同じ段を AI がやり直す |
| `results <task> --by <name> [--file <成果物>] -m "<観察>"` | 自分でやった段の結果・成果物を渡す（`handoff` → 次の段）。実行段は対話で できた/できなかった を入れる（T05） |
| `answer <task> --by <name> "<回答>"` | AI の質問に答える。止まった段から続き |
| `approve <task> --by <name>` | 最終承認 |
| `status` / `show <task>` / `web` | 一覧 ／ 1 件の詳細（根拠・履歴・誰が決めたか）／ ブラウザ |
