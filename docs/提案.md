# PMO 自律運用化 提案

作成日: 2026-08-12  
対象: VeriRAG PMO Agent（Django）  
判断したいこと: **人がPMO作業を都度実行する運用から、システムが検知・整理・下書き・追跡を自律的に行い、人は例外の確認と承認に集中する運用へ移行する。**

## 0. この文書の使い方

この文書は、要件・設計・実装順・テスト・エージェント用ハーネスを一体化した実行仕様である。実装エージェントは、章 11 の作業キューを上から一件ずつ実施し、章 12 の受入条件と章 13 のハーネスを通るまで次のチケットへ進んではならない。

実行時の唯一の正は、本文に加えて以下の機械可読パッケージである。人が決める必要がある項目は `decision_required` として実行不能にしてあるため、低コストモデルが推測で外部操作や本番有効化へ進む余地を作らない。

- `docs/agent/pmo_autopilot_contract.json` — 状態機械・ポリシー・禁止事項の不変契約
- `docs/agent/pmo_autopilot_decisions.json` — 未決定事項と、それをブロックするチケット
- `docs/agent/pmo_autopilot_queue.json` — 変更可能範囲・禁止操作・検証・レビューを持つ実行キュー
- `docs/agent/pmo_autopilot_scenarios.json` — 必須の事故・安全シナリオ 14 件
- `docs/agent/PMO_AUTOPILOT_RESUME.md` — 再開手順
- `docs/agent/PMO_AUTOPILOT_GOAL.md` — goal コマンドへ渡す固定指示
- `tools/pmo_autopilot_harness/` — 上記の整合・停止・独立レビューを強制する CLI

実装時に仕様の空白を推測で埋めない。次のいずれかに当たる場合は、`decision_required` として停止し、選択肢・影響・推奨案を記録して人に確認する。

- 外部システムへの書き込み、通知送信、チケット起票、担当者変更を自動化したい。
- 金額、期限、スコープ、優先度、品質ゲート、担当者に影響する判断を自動化したい。
- 根拠が古い、矛盾する、または不足する。
- テナント・案件・ロールの境界を確信できない。

## 1. 調査結果と結論

### 結論

現行システムには、PMO 自律化の部品が既に多くある。具体的には、ルールベースの予兆検知、根拠付き AI 提案、Agentic Trace、根拠不足時の承認ブロック、成果物の下書き・差分・承認履歴、外部連携、RBAC、既存の開発エージェント・ハーネスである。

一方で、それらは画面単位・都度実行の支援として存在している。**「いつ、何を、どの根拠で、どこまで自動で進め、誰に何だけ確認させるか」を一つの仕事として管理する中核がない。** そのため、現状は AI 提案 27 件すべてを人が一件ずつ探して判断する画面になっており、PMO の仕事を奪う運用にはまだ届かない。

最優先で足すべきものは、既存の `Alert`、`InterventionProposal`、`AgentRun`、`Deliverable` を置き換えない **PMO 自律作業（PMO Work Item）** と、その実行を統制する **自動化ポリシー・承認パケット・実行ハーネス** である。

### 現在確認したコード上の事実

- 検知は `run_detection()` が重複排除・上限・保存を担うが、定期実行・失敗時の再試行・案件別 SLA は持たない。
- `InterventionProposal` は人の採用／修正採用／不採用を残せるが、提案の集合を一つの案件対応として束ねず、採用後に誰がいつ何をするかを追跡しない。
- `EvidenceEvaluation.blocks_approval` により、根拠不足や矛盾がある成果物を承認させない安全弁はある。ただし、根拠の鮮度、対象範囲、版、競合の解消責任は統一管理されない。
- 成果物は AI 本文と確定本文を分離し、承認履歴も残る。しかし、定例時刻に自動で下書きを作り、差分・未解決事項・承認者だけを通知する運用ループはない。
- 既存の `tools/agent_harness/` は開発作業を安全に再開・検証するための良い基盤であり、今回の実装にも流用する。ただし、プロダクト内の自律実行の安全性を検証するシナリオ・偽コネクタ・ポリシー判定は未整備である。
- 実画面確認時の Django 起動ログで `agents` の未適用 migration が 1 件検出された。P0 の自律実行を載せる前に、migration 一貫性をリリース必須ゲート（A-26 / PA-10）として実行する。

### この提案で達成する運用

```text
外部同期・定刻・データ更新・手動依頼
              ↓
検知 / 根拠収集 / データ品質確認
              ↓
PMO Work Item（重複排除・優先度・期限・方針）
              ↓
自動実行できる安全な作業 ───→ 下書き・内部タスク・再計算・監視
              ↓
確認・承認が必要な例外 ─────→ 人の「承認センター」
              ↓
実行結果・外部反映・効果測定・監査・次回の改善
```

人が毎日行っていた「情報を集める」「差分を探す」「定例資料を組み立てる」「抜けを催促する」「状況を転記する」は自動化対象とする。人に残すのは、方針変更、優先順位・予算・期限の決定、対外送信・外部書き込みの承認、根拠が競合する例外の判断である。

## 2. 目標・非目標・成功指標

### 目標

1. システムは、定刻・データ変更・同期失敗を契機に PMO 作業を自ら作成し、根拠と次の処理を付けて進める。
2. 人は「全件を読む」のではなく、ポリシー上確認が必要な例外だけを確認・承認する。
3. すべての自動処理は、対象、入力版、根拠、ポリシー、実行結果、再試行、最終判断者を監査可能にする。
4. 根拠不足、根拠競合、データ鮮度切れ、権限外、未定義の外部書き込みは、成功扱いにせず安全に保留する。

### 非目標

- P0 で外部システムへ無承認で書き込むこと。Jira、Slack、Teams、Confluence、Git への変更・送信は、明示承認なしでは行わない。
- LLM の自由生成だけで事実認定や優先順位を決めること。根拠と決定規則のない文章は実行計画に採用しない。
- 現存する `Alert`、`InterventionProposal`、`AgentRun`、`Deliverable` を破壊的に置換すること。新モデルはそれらを関連付ける。
- 「自動化率」を、人が確認すべき高リスク操作を無理に自動化して達成すること。

### 初期 KPI（基準値を導入後 4 週間で確定）

| 指標 | 定義 | P0 の判定 |
|---|---|---|
| 自動完結率 | 完了した Work Item のうち、人の判断なしで安全に完結した件数 ÷ 完了件数 | 低リスク作業で 60% 以上。高リスクを無理に含めない。 |
| 人の確認時間 | 承認センターで一件を理解して判断する中央値 | 現行の個別画面巡回より 50% 以上短縮。 |
| 期限内処理率 | SLA 以内に完了または適切にエスカレーションした Work Item ÷ 全件 | 95% 以上。 |
| 根拠不備流出 | 根拠不足・矛盾があるのに外部反映または承認済みになった件数 | 0 件。 |
| 重複作業率 | 同一 `dedupe_key` の有効 Work Item が同時に複数存在した件数 | 0 件。 |
| 報告下書き自動作成率 | 期限までに下書きと差分が自動生成された定例報告 ÷ 対象定例 | 95% 以上。 |

## 3. 自動化の権限モデル

すべての Work Item と Step に、下表の `automation_level` を必ず保存する。画面表示だけで制御せず、サービス層で同じ判定を行う。

| レベル | 名前 | システムができること | 人が必要なこと |
|---|---|---|---|
| `observe` | 観測 | 読み取り、検知、根拠収集、シミュレーション、下書き生成 | 不要 |
| `internal_apply` | 内部反映 | 内部の下書き、再計算、Work Item、確認依頼の作成。取り消せる状態だけ。 | 不要 |
| `confirm` | 確認待ち | 実行計画・根拠・差分を提示し、期限まで確認を待つ。 | 担当者の確認 |
| `approve` | 承認待ち | 外部送信、外部書き込み、期限・優先度・スコープ・コストに影響する操作を準備する。 | 権限者の明示承認 |
| `prohibited` | 禁止 | いかなる条件でも自動実行しない。 | 人が別手段で実施 |

### P0 の既定ポリシー

- `observe` と `internal_apply` のみ自動実行可能にする。
- 外部通知、外部チケット更新、成果物の配布、承認済み本文の変更、担当者・期限・優先度の変更は常に `approve` とする。
- 根拠不足、根拠競合、入力鮮度切れ、権限不明、失敗 3 回到達は `prohibited` 相当の `hold` へ遷移させ、人へエスカレーションする。
- テナント既定値より緩いポリシーは、テナント管理者だけが作成・有効化できる。案件ポリシーはテナント既定値を緩められない。

## 4. 必要なドメイン設計

### 4.1 追加するモデル

既存モデルとの責務を混ぜない。生成結果は既存モデル、運用の仕事と統制は新モデルに置く。

| モデル | 主なフィールド | 不変条件・用途 |
|---|---|---|
| `PmoWorkItem` | `tenant`, `project`, `kind`, `state`, `priority`, `risk_level`, `source_type`, `source_key`, `dedupe_key`, `owner`, `due_at`, `policy_snapshot`, `correlation_id` | `(tenant, dedupe_key, is_active)` が一意。同じ問題を複数の人・エージェントが処理しない。 |
| `WorkPlan` | `work_item`, `version`, `summary`, `automation_level`, `state`, `created_from_run` | Plan は追記型。承認後に内容を変えたら新しい版を作る。 |
| `WorkStep` | `plan`, `order`, `kind`, `input_snapshot`, `idempotency_key`, `state`, `attempt_count`, `next_retry_at`, `result_summary` | 一度成功した同じ `idempotency_key` を再実行しない。 |
| `EvidenceBundle` | `work_item`, `source_type`, `source_ref`, `captured_at`, `expires_at`, `content_hash`, `scope`, `confidence`, `conflict_group` | 承認・外部反映時に鮮度とスコープを再検証する。本文全文は既存保存先を参照し、秘密値を複製しない。 |
| `AutomationPolicy` | `tenant`, `project`, `work_kind`, `risk_level`, `automation_level`, `required_role`, `max_age_minutes`, `version`, `enabled` | 最も厳しい一致規則を採用。評価結果を Work Item にスナップショット保存する。 |
| `ApprovalRequest` | `work_item`, `plan_version`, `requested_action`, `diff_summary`, `required_role`, `status`, `expires_at`, `decided_by`, `decision_reason` | 根拠・plan 版・対象が変われば失効。承認は一回だけで上書き不可。 |
| `ExecutionAttempt` | `step`, `started_at`, `ended_at`, `outcome`, `failure_category`, `safe_summary`, `external_receipt` | 失敗も必ず保存。秘密値・認証値・生本文を保存しない。 |
| `WorkLink` | `work_item`, `alert`, `proposal`, `agent_run`, `deliverable`, `approval`, `integration_job` のいずれか | 既存モデルとの関係を正規化して、画面と監査を横断可能にする。 |

### 4.2 Work Item の種別

P0 では下記に限定する。種別を増やす場合は、必ずポリシー・受入条件・テストシナリオを同時に追加する。

| `kind` | 起点 | 自動処理の終点 | 初期リスク |
|---|---|---|---|
| `detection_triage` | 予兆検知・アラート | 重複統合、根拠収集、提案・確認依頼の作成 | medium |
| `data_quality_repair` | 期限、担当、勤務カレンダー、依存、入力規則の欠落 | 不足データの担当者別確認依頼、再計算予約 | low |
| `forecast_review` | 予測変化・算定不能 | 差分、影響範囲、根拠、要確認事項の作成 | medium |
| `report_cycle` | 定例時刻・データ更新 | 下書き、前回差分、事実チェック、承認依頼の作成 | medium |
| `approval_followup` | 承認期限・差し戻し | 期限通知の下書き、保留、再依頼準備 | medium |
| `integration_recovery` | 同期失敗・鮮度 SLA 超過 | 再試行計画、影響範囲、管理者確認依頼の作成 | medium |
| `knowledge_quality` | RAG 根拠不足・古い索引 | 再索引候補、文書不足・競合の確認依頼 | low |

### 4.3 状態機械

状態遷移は `services/workflow.py` の一か所に閉じ、ビュー、管理コマンド、定期ジョブ、API が直接 `update()` してはならない。

```text
new
 └─> assessing ─> planned ─> auto_running ─> awaiting_confirmation ─> awaiting_approval ─> executing ─> completed
                   │                │                    │                    │
                   │                ├─> hold <───────────┴────────────────────┤
                   │                └─> failed ─> retry_scheduled ───────────┘
                   └─> cancelled

completed / cancelled / hold は終端状態。
hold のみ、権限者が理由を残して planned へ戻せる。
```

必須遷移条件:

1. `assessing → planned` は、対象スコープ、根拠、ポリシー評価、`dedupe_key` が存在するときだけ許可する。
2. `planned → auto_running` は、全 Step が `observe` または `internal_apply` のときだけ許可する。
3. `planned → awaiting_confirmation` は、少なくとも一つの `confirm` Step があるときだけ許可する。
4. `awaiting_approval → executing` は、未失効の `ApprovalRequest` が `approved`、根拠が鮮度内、plan 版が一致、実行者が必要ロールを満たすときだけ許可する。
5. 同一 `failure_category` が 3 回連続、または credential / permission / policy の失敗は再試行せず `hold` にする。
6. `completed` は、すべての必須 Step が `succeeded` または明示的な `skipped` 理由を持つときだけ許可する。

### 4.4 ポリシー評価の決定表

| 条件 | 結果 | 理由の保存先 |
|---|---|---|
| テナント・案件・対象が一致せず、または権限が不足 | `hold` | `ExecutionAttempt.failure_category=permission` |
| 根拠が欠落・期限切れ・スコープ外 | `awaiting_confirmation` | `EvidenceBundle` と `WorkItem.block_reason` |
| 同じ結論を支持・否定する根拠が競合 | `awaiting_confirmation` | `conflict_group` と比較結果 |
| Step が外部書き込み／通知／期限・優先度変更 | `awaiting_approval` | `ApprovalRequest.requested_action` |
| Step が内部下書き、再計算、内部 Work Item 作成 | `auto_running` | `policy_snapshot` |
| 同一有効 `dedupe_key` が存在 | 新規作成しない。既存に `evidence` を関連付ける。 | `WorkLink` |

## 5. アーキテクチャ

### 5.1 境界

```text
Event sources
  Alert / IntegrationJob / schedule / data-change / user request
      ↓
apps.pmo_automation.intake       : 重複判定、Work Item 作成
apps.pmo_automation.planning     : 既存 AgentRun と根拠を使い Plan を作る
apps.pmo_automation.policy       : 一意の自動化可否判定
apps.pmo_automation.workflow     : 状態遷移とロック
apps.pmo_automation.executor     : Step 実行、再試行、Outbox 作成
apps.pmo_automation.selectors    : 承認センター・SLA・監査の参照
      ↓
既存 apps/dashboard / agents / pmo / documents / integrations / audit
```

新アプリ名は `apps/pmo_automation` とする。`dashboard` は検知、`agents` は推論と根拠、`pmo` は成果物と承認、`integrations` はコネクタ、`audit` は操作監査という既存責務を維持する。自律運用だけを理由に既存アプリの責務を移さない。

### 5.2 イベントと冪等性

P0 は Django 管理コマンドによるポーリングで開始する。常駐ワーカー、Celery、Redis を同時に導入しない。

- `manage.py run_pmo_automation --tenant <slug> --dry-run` はイベント収集・計画・ポリシー判定まで実行し、一切保存しない。
- `manage.py run_pmo_automation --tenant <slug>` はトランザクション内で Work Item と安全な内部 Step だけを保存・実行する。
- `manage.py process_pmo_work --tenant <slug> --limit 50` は期限到来の Work Item を処理する。
- 各イベントには `source_type + source_key + policy_version` から導く決定的な `dedupe_key` を使う。
- `select_for_update(skip_locked=True)` 相当で一 Work Item を一ワーカーだけが実行する。SQLite で利用できない場合は、楽観ロック用 `lock_version` と条件付き更新で同じ効果を作る。
- 外部書き込みを P1 以降で有効化するときも、直にコネクタを呼ばず `OutboxEvent(idempotency_key, payload_hash)` を経由する。

### 5.3 根拠契約

根拠は「リンクが一件ある」だけでは十分ではない。`EvidenceBundle` ごとに次を保存し、実行直前に再評価する。

| 項目 | ルール |
|---|---|
| `source_ref` | 元レコード URL または UUID。表示専用文字列を主キーにしない。 |
| `scope` | テナント・案件・対象タスク／成果物を明示する。 |
| `content_hash` | 取得時点の内容を識別する。実行前に変われば承認を失効させる。 |
| `captured_at` / `expires_at` | ポリシーの `max_age_minutes` を越えたら再取得または確認待ち。 |
| `confidence` | 既存 `EvidenceEvaluation` の値を転記せず、元 `AgentRun` へのリンクを持つ。 |
| `conflict_group` | 同じ主張に対する肯定・否定の根拠を同一グループにして、人が比較できるようにする。 |

### 5.4 承認パケット

人に表示するのはエージェントの長い思考過程ではなく、必ず以下の固定 7 項目である。

1. 何を実行するか（動詞＋対象）。
2. なぜ今必要か（検知時刻、SLA、影響）。
3. 実行前後の差分。
4. 根拠（最大 5 件、鮮度・競合・不足を併記）。
5. 実行しない場合の影響。
6. 自動化レベルと必要な承認ロール。
7. 承認／差し戻し／却下／保留の選択肢と理由欄。

承認済みの対象、plan 版、根拠ハッシュ、ポリシー版のいずれかが変わったら、古い承認を `expired` にして再承認を要求する。

## 8. P0 の詳細要件

### FR-01: Work Item の作成と重複排除

- システムは `Alert`、`IntegrationJob` 失敗、予測算定不能、報告時刻を入力に Work Item を作成する。
- `dedupe_key` が同じ有効 Work Item がある場合、新規作成せず、根拠を既存 Work Item に追加する。
- 作成時に tenant、project、source、対象、priority、risk_level、policy_snapshot、correlation_id を必須とする。
- 一つの Work Item は複数の既存 `Alert`／`InterventionProposal`／`AgentRun`／`Deliverable` を持てる。

### FR-02: 計画・ポリシー・安全な自動実行

- `WorkPlan` は既存の `AgentRun` とルールベースの計画を利用して作る。LLM がなくても同じ状態遷移を完走する。
- Step ごとに目的、対象、入力スナップショット、期待結果、idempotency key、automation level を持つ。
- policy 評価は Step 実行の直前にも行う。画面表示時の判定結果を信用してはならない。
- `observe`／`internal_apply` 以外は Work Item を `awaiting_confirmation` または `awaiting_approval` にして停止する。

### FR-03: 承認センター

- `/pmo/approval-center/` を追加し、確認待ち・承認待ち・期限超過・保留を優先順に表示する。
- 行ごとに、承認パケットの 7 項目、関連 Work Item、Trace、成果物、元データを開ける。
- 一括操作は、同一テナント・同一案件・同一 policy version・同一 requested action・根拠鮮度内・同一 required role のセットだけに許可する。
- 承認・却下・差し戻し・保留には理由を必須とする。高リスク Work Item は作成者または最後の実行者が承認できない。

### FR-04: 定例報告の自動サイクル

- 案件ごとに報告周期、締め時刻、対象期間、承認ロールを設定できる。
- 締め時刻に `report_cycle` Work Item を作り、数値スナップショット、前回差分、未解決 Work Item、根拠評価を生成する。
- 承認済み本文を再生成で変更しない。次版の下書きを作る。
- 事実チェック不能・根拠競合・必要データ不足は、送付ではなく承認センターの確認待ちにする。

### FR-05: データ品質の自律修復

- 勤務カレンダー、担当者、期限、進捗、依存関係、更新期限の欠落を検出する。
- 自動で値を推測して確定しない。担当候補・必要入力・影響範囲を持つ確認依頼を作る。
- 入力が確定したら、関連する予測・品質評価・報告下書きを再実行し、以前の結論との差分を記録する。

### FR-06: 失敗・停止・監査

- 資格情報、権限、ポリシー、入力検証、外部一時障害、未知の失敗を分類する。
- 資格情報・権限・ポリシーは即 `hold`、一時障害は指数バックオフで最大 3 回、未知の失敗も 3 回で `hold` とする。
- 停止時は、復旧に必要な担当ロール、失敗要約、関連接続／対象、再開可能な条件を表示する。
- すべての遷移・承認・Step 実行・外部受領証跡を `OperationLog` と相関付ける。

### FR-07: ロールと職務分掌

| 操作 | 許可するロール |
|---|---|
| observe / internal_apply の実行 | システム（ポリシー許可時） |
| 確認待ちへの回答 | 案件 PMO、案件責任者、または対象データの担当者 |
| 高リスク承認・外部反映承認 | テナント管理者または案件責任者。作成者・実行者本人は不可。 |
| ポリシー緩和・停止解除 | テナント管理者のみ |
| 監査閲覧 | 現行 RBAC と案件スコープに従う |

## 9. API・コマンド・画面契約

P0 はテンプレート画面を維持し、同じサービス層の上に小さい JSON API を追加する。画面の POST はこのサービスを呼ぶだけにする。

| 操作 | 契約 |
|---|---|
| `POST /pmo/approval-center/<uuid>/decide/` | `{decision: approved|rejected|returned|hold, reason, plan_version}`。plan 版・根拠・ポリシーが一致しなければ 409。 |
| `POST /pmo/work-items/<uuid>/resume/` | `hold` のみ。理由と現在の policy version が必要。 |
| `GET /pmo/work-items/<uuid>/` | Work Item、Plan、Step、Evidence、Approval、既存リンク、監査相関を返す／表示する。 |
| `POST /pmo/work-items/<uuid>/dry-run/` | 保存せず、現在の根拠・policy で実行可能性と差分を返す。 |
| `manage.py run_pmo_automation --tenant <slug> [--dry-run] [--kind <kind>]` | intake→assess→plan→policy。`--dry-run` は DB を変更しない。 |
| `manage.py process_pmo_work --tenant <slug> --limit <n>` | 実行可能な Step のみを処理。承認・外部反映は実行しない。 |
| `manage.py pmo_automation_status --tenant <slug>` | 状態別件数、SLA 超過、次回再試行、保留理由、ポリシー版を機械可読 JSON と人可読で返す。 |

エラー契約:

- 401/403/404 の現行情報秘匿ルールを維持する。
- `409 conflict` は、plan 版、根拠ハッシュ、ポリシー版、状態のいずれが変わったかを安全な短文で示す。
- 機密情報、接続トークン、外部本文、内部例外スタックを画面・監査ログ・API 応答へ出さない。

## 12. 受入条件（Given / When / Then）

1. **重複排除**  
   Given 同一案件・同一対象の有効 Work Item がある。When 同じ検知が再到着する。Then 新規 Work Item は作られず、既存 Work Item に根拠リンクだけが追加される。

2. **テナント隔離**  
   Given テナント A と B に同じ `dedupe_key` がある。When A の自律実行を行う。Then B の Work Item、根拠、承認、監査は参照も更新もされない。

3. **根拠不足**  
   Given Plan に必要な根拠が欠落している。When 自動実行を評価する。Then Step は実行されず、Work Item は `awaiting_confirmation` になり、不足内容を示す。

4. **根拠変更**  
   Given 人が plan v1 を承認している。When 根拠ハッシュまたは plan が v2 へ変わる。Then v1 の承認は `expired` になり、実行できない。

5. **低リスク内部作業**  
   Given policy が `internal_apply` を許可し、根拠が鮮度内である。When `process_pmo_work` を実行する。Then 内部下書きまたは再計算だけが一度実行され、相関付き監査が残る。

6. **外部反映の安全性**  
   Given Step が外部通知または外部更新である。When 人の承認がない。Then コネクタは呼ばれず、Work Item は `awaiting_approval` のままである。

7. **職務分掌**  
   Given 高リスク Work Item の plan を作成または最後に実行した利用者がいる。When その利用者が承認しようとする。Then サーバ側で拒否し、理由を監査に残す。

8. **同時実行**  
   Given 二つのワーカーが同じ実行可能 Step を取得する。When 同時に処理する。Then 一方だけが成功し、外部・内部とも二重実行されない。

9. **失敗回復**  
   Given 一時的な外部障害が起きる。When 三回まで失敗する。Then backoff を置き、三回目で `hold`、以後自動再試行しない。

10. **資格情報失敗**  
    Given credential または permission の失敗が起きる。When 実行する。Then 一回目で `hold`、再試行予約は作られず、管理者向け Work Item が作られる。

11. **報告自動化**  
    Given 報告締め時刻である。When 安全なポリシーで実行する。Then 対象スナップショット・差分・事実チェックを持つ下書きができ、承認が必要なら承認センターへ出る。

12. **算定不能の修復**  
    Given 勤務カレンダー未設定で予測が算定不能である。When 自律実行を行う。Then 値を勝手に補わず、必要入力と影響を持つ `data_quality_repair` を作る。

13. **dry-run**  
    Given 任意のテナントで `--dry-run` を実行する。When 処理が終了する。Then DB レコード、OperationLog、外部呼び出し、ファイルに変更がない。

14. **監査追跡**  
    Given 完了または保留の Work Item がある。When Work Item 詳細を開く。Then 起点、計画、根拠、policy、各試行、承認、既存 Agent Trace、成果物、最終結果へ遷移できる。

### 13.4 必須シナリオ

| シナリオ ID | 名称 | 期待する不変条件 |
|---|---|---|
| H-01 | 同一 Alert 再到着 | Work Item は一件、根拠リンクだけ増える。 |
| H-02 | テナント越境 | A の実行が B のデータに 0 件の影響。 |
| H-03 | 古い根拠 | approval／外部 Step が実行されない。 |
| H-04 | 根拠競合 | `awaiting_confirmation`、人が競合根拠を比較可能。 |
| H-05 | 低リスク自動実行 | 内部下書き一回、再実行しても一回。 |
| H-06 | 未承認外部更新 | fake connector の呼出回数 0。 |
| H-07 | 承認失効 | plan 又は根拠変更で approval は expired。 |
| H-08 | 職務分掌 | 作成者／実行者の自己承認を拒否。 |
| H-09 | 一時失敗 | 三回で hold、四回目は実行しない。 |
| H-10 | credential 失敗 | 一回で hold、再試行なし。 |
| H-11 | dry-run | DB、監査、fake connector の全スナップショット不変。 |
| H-12 | 報告サイクル | 下書き・差分・事実チェック・承認依頼を追跡可能。 |
| H-13 | 算定不能 | 値の捏造なし、データ品質 Work Item が生成。 |
| H-14 | 画面操作 | 承認センターでキーボード操作、理由必須、状態更新後に即反映。 |

### 13.5 実装エージェントへの固定手順

1. `docs/agent/pmo_autopilot_queue.json` と `docs/agent/PMO_AUTOPILOT_RESUME.md` を読む。
2. `next` が返した一件だけを `in_progress` にする。依存未完了や `decision_required` を迂回しない。
3. `allowed_paths` の外を変更する必要が出たら、理由と影響を記録して停止する。
4. 先に失敗するテストまたはハーネスシナリオを一件追加する。
5. 最小実装を行い、当該テスト→関連テスト→必要な管理コマンド dry-run の順に検証する。
6. migration、権限、外部副作用、状態遷移、画面操作のいずれかに触れたら、対応するレビューを埋める。
7. 検証名と結果を `evidence` に記録し、独立レビューが承認して初めて `done` にする。
8. 同じ原因の失敗が三回続いたら修正を続けず `hold` にする。秘密情報・実外部システムを調べない。

### 13.6 完了ゲート

P0 の完了を宣言できるのは、次が全て満たされたときだけである。

- H-01〜H-14 が通る。
- `apps/pmo_automation` のモデル／サービス／コマンド／画面テストが通る。
- 既存の `apps/core/tests/test_agent_harness.py` を含む既存回帰が通る。
- tenant 境界、外部未承認、dry-run 不変、自己承認拒否のテストが存在する。
- 承認センターと Work Item 詳細の実画面を、通常データ、根拠不足、承認失効、保留の 4 状態で撮影・確認している。
- ポリシー緩和、外部送信、資格情報の設定を含む実運用試験は、人の明示承認なしに実施していない。

## 14. 段階導入と切戻し

| 段階 | 有効化するもの | 人の確認 | 次段階へ進む条件 | 即時切戻し |
|---|---|---|---|---|
| 0. Shadow | intake・計画・policy を `dry-run` だけで実行 | 毎日サンプル照合 | 重複、越境、根拠不備流出が 0 | 全ジョブ停止 |
| 1. Observe | Work Item と承認パケットを作成 | PMO が既存運用と並行比較 | 優先順位と根拠の妥当性を合意 | `observe` を無効化 |
| 2. Internal apply | 下書き、再計算、内部確認依頼だけを自動化 | 例外だけ確認 | 自動完結率・失敗率・確認時間が KPI を満たす | tenant を `observe` へ戻す |
| 3. Controlled approval | 承認センターと限定した Outbox を有効化 | 権限者が毎回明示承認 | 二重送信 0、失効承認 0、SLA 95% 以上 | Outbox 停止、未送信を hold |
| 4. Expansion | 承認済みの仕事種別を一つずつ増やす | 月次ポリシーレビュー | 各種別の shadow 比較・受入条件を満たす | 当該 policy version を無効化 |

切戻しはデータ削除で行わない。`AutomationPolicy.enabled=false` と全実行可能 Work Item の `hold` 遷移で止め、既存の証跡を保持する。

## 15. 最初に人が決めるべき事項

実装を始める前に、以下だけは業務責任者が決定する必要がある。決まるまでの既定は本文の P0 方針（外部反映なし、低リスク内部作業のみ）とする。

1. 最初の対象テナントと対象案件をどれにするか。
2. 報告の種別ごとの締め時刻、承認者、承認期限。
3. `internal_apply` として自動で許可する内部操作の一覧。
4. 誰がテナント管理者、案件責任者、確認者、承認者になるか。
5. P1 で最初に承認付き外部反映を許可する一操作（例: Slack 下書き、Jira コメント下書き）を何にするか。

これらが未決定でも、PA-01〜PA-10 と Shadow 段階までは実装・検証できる。外部反映とポリシー緩和だけは決定なしに進めない。
