# UIデザイン テスト観点表

VeriRAG PMO Agent の画面を検査するための観点表。
**再利用を前提に、各観点へ「完了条件」と「確認方法」を持たせる。**
主観の良し悪しではなく、満たしたか満たさないかを判定できる形にしてある。

## 出所

書籍『UIデザイン 改善のヒント』の該当ページ写真 34 枚。
うち 3 枚は同一ページの撮り直しのため、実質 31 ページ・11 節から起こした。

| 節 | 内容 | 観点 |
|---|---|---|
| CHAPTER 2-07 | アイコンの使い方 | VP-01 〜 VP-04 |
| CHAPTER 3-02 | ヘッダー、ナビゲーション、ボタン | VP-05 〜 VP-08 |
| CHAPTER 5-01 | デスクトップアプリのページレイアウト | VP-09 〜 VP-13 |
| CHAPTER 5-03 | 画面に情報を詰め込みすぎない | VP-14 〜 VP-18 |
| CHAPTER 5-04 | 視線の流れに沿う | VP-19 〜 VP-21 |
| CHAPTER 5-05 | 画面のグループ分けと情報の精査 | VP-22 〜 VP-24 |
| CHAPTER 5-07 | テキストは画面幅いっぱいにしない | VP-25 〜 VP-29 |
| CHAPTER 5-10 | 一覧を見やすくする | VP-30 〜 VP-35 |

| （書籍外） | ISO 9241-110 対話の原則で補う | VP-62 〜 VP-63 |

外部体系との照合（自作の枠組みにしないため）:

- WCAG 2.2（1.4.10 リフロー、2.4.7 フォーカスの可視化、3.2.4 一貫した識別）
- ISO 9241-110（適合性・自己記述性・制御性・エラー耐性）

書籍は「操作への応答」と「失敗からの回復」を扱わないため、VP-62・VP-63 を ISO 側から補った。

## 使い方

1. 画面を追加・変更したら、この表を上から確認する。
2. `自動` 列が「可」の観点は、テストが緑であることを以て完了とみなす。
3. 目視でしか判定できない観点は、スクリーンショットを撮って確認する。
   「確認した」とだけ書いて済ませない。
4. **このシステムに該当しない観点も削除しない。** 該当しない理由を書いて残す。
   将来モバイル対応や編集ツールを持ったときに、抜けとして戻ってくるため。

# CHAPTER 2-07 アイコンの使い方

## VP-01 アイコンで機能を想像させ、文字量を減らす

**書籍** 多くは機能を説明する補助として使われ、文字を読まずともアイコンだけで機能を想像できる。
文字のスペースを節約でき、文字ばかりの画面よりすっきり見せられる。

**完了条件**
1. 繰り返し現れる操作（削除・編集・追加・戻る）が、毎回同じアイコンで示される。
2. アイコンを添えたことで、ラベル文字が短くなっている（アイコンと同義語の重複がない）。

**確認方法** テンプレートのアイコン使用箇所を grep し、同じ操作に別アイコンが使われていないか照合。
**自動** 一部

## VP-02 ナビゲーションにアイコンを置き、できることの全体像を示す

**書籍** 特にサイドナビゲーションやスマホのボトムナビゲーションにアイコンを配置することは効果的で、
そのアプリでできる全体像を説明することができる。

**完了条件**
1. サイドナビの親カテゴリすべてにアイコンがある（一部だけ無い、が無い）。
2. アイコンがカテゴリの内容を表しており、連番や記号の代用になっていない。

**確認方法** `apps/core/navigation.py` の全 NavSection に `icon` または代替表現があること。
**自動** 可

## VP-03 世の中で定着したアイコンを、定着した意味どおりに使う

**書籍** 矢印＝画面の遷移や開閉、3本線＝メニュー、!マーク＝注意やエラー、グローバル＝多言語やネットワーク、
家＝HOME/TOP、カート＝購入前のカゴ、ゴミ箱＝削除、右向き三角・2本線＝再生と一時停止。
これらはユーザーも他のアプリで見慣れており、すでに意味を理解している。

**完了条件**
1. 上記の定番アイコンを、書籍の意味と異なる用途に使っていない。
2. 「!」を注意・エラー以外（例: 情報の補足）に使っていない。

**確認方法** アイコン使用箇所の目視。
**自動** 不可

## VP-04 めずらしいアイコンは文字とセットで置く

**書籍** あまり見ないアイコンを使うときは、文字もセットで置く。
よほど一般的なアイコンでなければ、文字情報とセットで配置しないとユーザーには伝わらない。
ツールチップなどを活用し、アイコンボタンにも文字を追加する。

**完了条件**
1. アイコンのみのボタン・リンクが存在しない。存在する場合は `aria-label` とツールチップの両方を持つ。
2. 同梱フォントに無いグリフを指定していない（指定名がそのまま文字として表示されない）。

**確認方法** `apps/core/tests/test_help_components.py`、`templates/partials/nav_icon.html` の分岐。
**自動** 可

# CHAPTER 3-02 ヘッダー、ナビゲーション、ボタン

## VP-05 色が際立つ3箇所（ヘッダー・ナビ・ボタン）を統一する

**書籍** Web アプリでは過度な装飾は不要なため、印象を与えられる要素が限られる。
ヘッダーとナビゲーションは画面が移動しても必ず表示され、ユーザーの目に常に入る。
ボタンはほぼすべてのページで登場し、色が乗る面積が大きい。
ここで色がバラバラになるとデザインの統一感が崩れる。

**完了条件**
1. ヘッダー背景・現在地ナビ・主ボタンが、それぞれ CSS 変数を経由して色を得る。生の hex 直書きが無い。
2. 「現在地」を示す色が 1 種類である（複数の値に分裂していない）。

**確認方法** `static/css/app.css` の色定義を grep。
**自動** 可

## VP-06 メインカラーは1色に決め、ベースは無彩色にする

**書籍** 色はメインのカラーを1色決めて配色するとうまくまとまる。
アプリの背景などベースの色は白や黒の無彩色で構成されているため、
ヘッダー・ナビゲーション・ボタンで色を用いて印象を整える。

**完了条件**
1. テーマ色を表す変数が1つで、そこから派生した濃淡以外の色をヘッダー・ナビ・主ボタンに使わない。
2. 背景が無彩色（白またはごく淡いグレー）である。

**確認方法** `:root` の変数一覧と使用箇所。
**自動** 可

## VP-07 配色パターンを1つ選び、それを守る

**書籍** よくある配色例は4つ。ロゴとボタンのテーマカラーを揃える／ヘッダーとボタンを揃える／
サイドナビゲーションとボタンをテーマカラーに揃える／サイドナビゲーションを黒系で引き締める。
白を使うと全体的にクリーンな印象に、黒を使うと引き締まった印象にできる。

**完了条件**
1. 採用した配色パターンが文書に明記されている（本システムは「ヘッダーとボタンを揃える」）。
2. 画面ごとにパターンが変わらない。

**確認方法** `docs/DesignSystem.md` の記載と実装の照合。
**自動** 不可

## VP-08 モバイルでも同じ原則を適用する（本システムでは非該当）

**書籍** モバイルアプリでも、ヘッダー・ナビゲーション・ボタンが重要。
特に下部の固定ナビゲーションはすべてのページで表示されるため重要。
アプリアイコンやスプラッシュ画像でブランドやテーマ色の印象を強く残せる。

**該当しない理由** 本システムはブラウザのみで、ネイティブアプリと下部固定ナビを持たない。
モバイル幅はレスポンシブで対応する（VP-28 と VP-46 で担保）。

**将来該当する条件** ネイティブアプリまたは PWA を出すとき。

# CHAPTER 5-01 デスクトップアプリのページレイアウト

## VP-09 4領域の役割分担を守る

**書籍** ヘッダー＝基本的に常に表示され、アプリ・サイトのロゴや全体に関わる機能が配置される。
ナビゲーション＝ヘッダー・左サイド、もしくはその両方に配置される。
ページヘッダー＝そのページの画面名や、ページ内でできる機能のボタン・タブが配置される。
コンテンツエリア＝そのページ独自の内容が掲載されるメインのエリア。右パネルを使うこともある。

**完了条件**
1. 全体に関わる機能（テナント切替・案件切替・ログアウト）がヘッダーにあり、本文に無い。
2. 画面固有の操作がページヘッダーにあり、本文に散らばっていない。
3. 画面名がページヘッダーに必ず出る。

**確認方法** `templates/layouts/base.html` のブロック定義と各画面の使用状況。
**自動** 可

## VP-10 すべてのページで一貫性を持たせる

**書籍** アプリ内のレイアウトを一貫性を持って揃えることで、ユーザーは都度学習する必要がなく、
他の画面の経験からアプリを使うことができる。

**完了条件**
1. 業務画面がすべて同じ base テンプレートを継承する。
2. 4領域の順序と位置が全画面で同一である。

**例外** ログイン画面・エラー画面は認証前でナビを持たないため別レイアウトを継承する。違反ではない。

**確認方法** `{% extends %}` の一覧。
**自動** 可

## VP-11 世の中に広まっているアプリの配置に揃える

**書籍** 一般的に世の中に広まっているアプリの配置に揃えることも有効なレイアウト手法。

**完了条件**
1. ロゴが左上、アカウント関連が右上にある。
2. 主ナビゲーションが左サイドにある。
3. 検索が上部にある。

**確認方法** ヘッダーのスクリーンショット。
**自動** 不可

## VP-12 2カラムにする場合、主エリアと副次エリアの強弱をつける

**書籍** 横幅が広いレイアウトでは2カラム、3カラムのレイアウトも可能。
その場合でも画面ごとのメインコンテンツは大きく配置し、
主体となるエリアと副次的な情報のエリアの強弱がユーザーに伝わるようにする。

**完了条件**
1. 2カラムの画面で、主カラムの幅が副カラムの 1.5 倍以上ある。
2. 副カラムの見出しが主カラムの見出しより小さい、または弱い色である。

**確認方法** 該当画面のスクリーンショット。
**自動** 不可

## VP-13 マウス操作前提のレイアウトにする

**書籍** マウスやトラックパッドを使うことが前提となり、マウスカーソルで操作しやすいレイアウトが求められる。

**完了条件**
1. クリック対象の高さが 32px 以上ある。
2. 隣接するクリック対象の間隔が 8px 以上ある。
3. 行全体がクリック対象の場合、ホバーで背景色が変わる。

**確認方法** ブラウザで実測。
**自動** 可

# CHAPTER 5-03 画面に情報を詰め込みすぎない

## VP-14 余白を大きくする

**書籍** アプリの UI において「簡単な印象」を与えるのに最も有効な手段のひとつ。

**完了条件**
1. カード間の余白が 16px 以上ある。
2. カード内の上下パディングが 14px 以上ある。

**確認方法** CSS の変数定義。
**自動** 可

## VP-15 文字サイズにメリハリをつける

**書籍** 文字サイズにメリハリをつけることが有効。

**完了条件**
1. 1画面で使う文字サイズが3段階以上ある（見出し・本文・補足）。
2. 見出しと本文のサイズ差が 1.25 倍以上ある。

**確認方法** CSS の font-size 一覧。
**自動** 可

## VP-16 ボタンの数を減らし、主要な操作はなるべくひとつにする

**書籍** 目に入る主要な操作はなるべく少なくなるように工夫する。

**完了条件**
1. 1画面に同時に出る主ボタン（`.btn-b`）が、**種類として1つ以下**。
   - 排他分岐で1つになるものは違反としない。
   - 一覧の行内で繰り返される同一操作は、1種類として数える。
     その画面の存在理由そのものの操作（承認画面の「承認」など）を主ボタンから降ろすと、
     次にやることが画面から読み取れなくなる。「少なく」は「無く」ではない。
   - ヘッダーの主操作と行内の主操作が**別の操作**なら、行内を `.btn-out` に降ろす。
2. ページヘッダーに置く操作が3つ未満。
3. 副操作は `.btn-out` / `.btn-ghost` を使う。
4. 主ボタンが1つも無い画面を作らない（その画面で何をすべきかが示されていない）。

**確認方法** テンプレートの `btn-b` 出現数を数える自動テスト。
**自動** 可

## VP-17 登録ステップは1画面に詰めず分割する

**書籍** 登録ステップなどは1画面で一気に入力させようとせず、
画面を分割することでより簡単な印象にすることができる。

**完了条件**
1. 入力項目が10を超えるフォームは、段階または折りたたみに分かれている。
2. 各段階に、いま何段目かの表示がある。

**確認方法** フォーム画面の入力項目数を数える。
**自動** 可

## VP-18 業務ツールでは余白を減らす判断もある（本システムの採用方針）

**書籍** 余白は必ずしも大きいほうが良いわけではない。
余白を小さくすると、その分多くの情報を画面に表示できる。
PC の扱いに慣れている人など、業務利用のアプリの場合は、
難しい印象であっても情報量が多いほうが使い勝手が良くなる場合がある。

**本システムの判断** PMO の業務ツールであり、一覧で件数を比較する用途が中心。
VP-14 の余白は確保しつつ、一覧の行高は詰める（行間より列の絞り込みで可読性を確保する = VP-31）。

**完了条件**
1. 一覧の行高が 40px 以下である。
2. その代わり、一覧の列数が VP-31 の上限を守っている。

**確認方法** ブラウザで実測。
**自動** 可

# CHAPTER 5-04 視線の流れに沿う

## VP-19 Z型: タイトル・メニューは左上、決定系アクションは右下

**書籍** ユーザーの視線がアルファベットの「Z」のように、左上→右上→左下→右下の順に進むパターン。
アプリではタイトルやメニューを左上、決定系のアクションボタンを右下に置くようにする。

**完了条件**
1. フォームの送信ボタンが、フォーム末尾の右寄せ位置にある。
2. 画面名が左上にある。

**確認方法** フォーム画面のスクリーンショット。
**自動** 一部

## VP-20 ネガティブなボタンはあえて左下に置いて印象を薄める

**書籍** 「削除」など、ネガティブなボタンは、あえて左下に置いて印象を薄めることもある。

**完了条件**
1. 削除・アーカイブ・却下が、送信ボタンと同じ見た目（`.btn-b`）で並んでいない。
2. 破壊的操作が、送信ボタンより左に置かれている。

**確認方法** `.actions` を持つテンプレートの目視と、クラス名の照合。
**自動** 一部

## VP-21 F型: サイドナビのある画面は、重要なものをリスト先頭に置く

**書籍** ユーザーの視線がアルファベットの「F」のように移動するパターン。
サイドナビゲーションが置かれている画面や SNS などでよく使われる。
下にいくほど読み飛ばされるようになるため、読み飛ばされないよう、重要なものはリスト先頭に配置する。

**完了条件**
1. 一覧の既定の並び順が「重要な順」（危険・期限切れ・未対応が先頭）である。
2. 更新日時など重要度と無関係な軸を既定の並び順にしていない。

**確認方法** 各一覧の既定 `order_by` を確認。
**自動** 可

# CHAPTER 5-05 画面のグループ分けと情報の精査

## VP-22 関連のある項目を近くに置いてグループ化する

**書籍** 項目は関連のあるものを近くに置くことで、ユーザーの理解を助ける。
例では「講座の内容」「講座の付加情報」「ログインユーザーの情報」と分類している。
この分類に沿って、似た内容の項目を近くに配置するようにレイアウトを調整する。

**完了条件**
1. 1つのカード内の情報が、意味の異なる3群以内に分かれている。
2. 群の境界が、見出し・区切り線・余白のいずれかで示されている。

**確認方法** カード構造の目視。
**自動** 不可

## VP-23 優先順位を決めて強弱をつける

**書籍** 項目をまとめたら強弱をつける。優先順位はアプリの目的によって異なる。
この優先順位に沿って、文字サイズや配置の調整、色の変更、ラベルの削除、
図やアイコンの追加などを考えていく。

**完了条件**
1. 各画面で最も重要な指標が、他より大きい文字または色付きバッジで示されている。
2. 優先度の低い情報からラベルが削られている（値だけで意味が通るものに「〜:」を付けない）。

**確認方法** 画面スクリーンショットによる目視。
**自動** 不可

## VP-24 読み飛ばしてよい情報が判断できる状態にする

**書籍** 強弱がないと、どの情報も等しく感じてしまう。
グループ化し優先順位をつけると、重要な項目が目に入り、読み飛ばしてもよい情報が判断しやすい。

**完了条件**
1. 補足情報が `.muted` / `.ps` など弱いスタイルで、主情報と視覚的に区別されている。
2. 1カード内で最も強いスタイルの要素が1つだけである。

**確認方法** テンプレートのクラス使用状況。
**自動** 一部

# CHAPTER 5-07 テキストは画面幅いっぱいにしない

## VP-25 1行は20〜30字、多くても40字

**書籍** 一行あたりの読みやすい文字数は20〜30文字程度と言われており、多くても40文字程度とされている。

**完了条件**
1. 本文・説明文の1行が全角40字を超えない（`max-width` を ch 単位で指定）。

**確認方法** `apps/core/tests/test_responsive.py`（ブラウザ実測）。
**自動** 可

## VP-26 コンテンツ幅で改行位置を調整する

**書籍** PC 画面はウィンドウが大きいため、コンテンツの幅にテキストが長く入ってしまう。
ログイン画面など、ある程度左右の余白に自由のきく画面であればコンテンツ幅を調整する。

**完了条件**
1. ログイン画面のコンテンツ幅が、業務画面より狭く設定されている。
2. 本文領域に `max-width` が設定され、画面幅いっぱいに広がらない。

**確認方法** CSS の `max-width` 指定。
**自動** 可

## VP-27 改行位置を制御する

**書籍** HTML の場合、`<br>` タグを用いてテキストの改行位置を開発側が自由に調整できる。
メールの文章を作るときのように、読みにくいと感じたら改行を入れて読みやすくする。

**完了条件**
1. 折り返し位置が句読点または助詞の直後に来る。単語や文節の途中で折れない。

# CHAPTER 5-10 一覧を見やすくする

## VP-30 一覧の項目に強弱をつけ、見出しの文字を大きくする

2. 状態を示す値がバッジなど色付きで示されている。

## VP-31 全部の情報は出さなくてよい

**書籍** 一覧には情報をすべて詰め込むべきではない。
ユーザーが対象を判断できる情報があれば十分。

## VP-32 横並び以外のレイアウトも考える

他のレイアウトができないか検討する。

**完了条件**
1. 各一覧について、テーブル型を選んだ理由が説明できる（比較が目的か）。

**確認方法** `docs/UIDesign.md` の記載。
**自動** 不可

## VP-33 一覧上に置くボタンを隠す

**書籍** 一覧すべてにボタンが並ぶと画面が複雑に見えるため、普段は隠し、

**完了条件**
1. 行内の操作ボタンが3つを超えない。
2. 3つに近い場合は、ホバー時のみ表示する。

**自動** 可

## VP-34 一覧の型を用途で選ぶ

**書籍**
- リストバー型: アイテム1枚の中を自由なレイアウトで配置。情報に強弱をつけやすくカスタマイズ性が高い。
  デメリットは少なく、迷ったらこの形式がお勧め。
- テーブル型: 表組み。列名でソート機能を持たせられる。カスタマイズ性は低く情報が単調に見えがち。
  会計明細や統計データなど、一覧性が重要で情報を比較しながら閲覧したい用途に向く。
- カード型: 写真のサムネイルを大きく見せたいときに使う。横並びで数を多く配置できる。
  文字情報を多く表示できないデメリットがある。

**完了条件**
1. 比較が目的の一覧はテーブル型を使っている。
2. 判断材料に強弱が要る一覧は、リストバー型を検討している。
3. 画像を持たない一覧にカード型を使っていない。

**確認方法** 各一覧の型と用途の対応表（`docs/UIDesign.md`）。
**自動** 不可

## VP-35 一覧と詳細を同時に表示するパターンを検討する

**書籍** PC のデスクトップアプリの場合は画面領域が広いため、画面を分割して一覧と詳細をセットで表示することがある。
代表例はメールアプリ。画面遷移を伴わず、一覧に並ぶ情報を次々と切り替えられるため、
連続して確認を行うアプリケーションに向いている。
左右分割型／上下分割型（モバイル）／ミニウィンドウ型（クリックやオンマウスで詳細をウィンドウ表示）。

**完了条件**
1. 連続確認が主目的の画面（承認待ち・判断待ち）で、分割表示を検討した記録がある。
2. 分割表示を採用する場合、左右それぞれのスクロールが独立している（VP-41）。

**確認方法** `docs/UIDesign.md` の記載。
**自動** 不可

# CHAPTER 5-11 詳細画面の表示パターン

## VP-36 詳細を1ページにする場合

**書籍** 最も基本の形で、詳細画面だけに操作を集中させることができる。画面全体を使うことができるため、

# CHAPTER 5-12 スクロール範囲のコツ

## VP-40 スクロール範囲を区切り線などで明確にする

**書籍** デスクトップアプリでは複数箇所にスクロールエリアを配置することがある。
その際、スクロールする領域がわかりやすくなるように、区切り線やドロップシャドウを追加する。
特に上下で分ける場合、エリアの境界で範囲に収まりきらない要素が見切れるため、
明確な範囲を示すためにも境界となる罫線を表示することを勧める。

**完了条件**
1. スクロールする領域の境界に、罫線または影がある。
2. 領域の境界が、カードの境界と一致している（どこまでが動くのか分かる）。

**確認方法** スクロール領域の CSS。
**自動** 可

## VP-41 サイドナビゲーションは別スクロールにする

**書籍** サイドナビゲーションを本体のコンテンツと一緒に配置するとき、
一緒にスクロールしてしまうとナビゲーションが途中から消えてしまう。
ナビゲーションには別スクロールを用意し、それぞれスクロールできるようにする。

**完了条件**
1. 本文を最下部までスクロールしても、サイドナビが画面に残る。
2. サイドナビ自体が長い場合、ナビ内で独立してスクロールする。

**確認方法** ブラウザで実測。
**自動** 可

## VP-42 スクロール領域の中に別のスクロール領域をなるべく作らない

**書籍** スクロールエリアは工夫すればどこにでも配置できるが、多用は禁物。
スクロールエリアが二重だと、マウスホイールの操作の途中でスクロールが止まるなど、挙動に違和感が出る。
本体のスクロールと干渉し、マウスホイールでの操作がしにくくなる。
可能なら、レイアウトを調整してエリアを分ける。

**完了条件**
1. 縦スクロール領域が入れ子にならない（`overflow-y: auto` の入れ子が無い）。
2. 横スクロールは表の中だけに閉じ、縦とは競合させない。

**確認方法** CSS の `overflow` 指定の入れ子を確認。
**自動** 可

## VP-43 固定すべきパーツを固定する

**書籍** 以下のパーツはスクロールさせず固定することを推奨する。
固定することで常にユーザーの目に入れることができる。
- ヘッダー: アプリの名前や検索ボックスなど、いつでもアクセスできるようにしたい領域
- ページヘッダー: そのページの名前やページ内の操作ボタン
- タブ、ナビゲーション: 固定表示することで画面の横移動がしやすくなる
- 下部の操作ボタン: モーダルなどで常に画面上に表示しておくと、いつでも操作でき負荷を下げられる
- 編集ツールのエリアのボタン: 操作の反映を確認しつつ作業できるようにする

**完了条件**
1. ヘッダーが常に表示される。
2. ページヘッダー（画面名と主操作）が本文スクロール時も残る。
3. 長いフォームの送信ボタンが、スクロールせずに押せる位置にある。

**確認方法** ブラウザで実測。
**自動** 可

## VP-44 固定しすぎて領域を圧迫しない

**書籍** ただし、固定できる領域を圧迫してしまうため、やりすぎには注意が必要。

**完了条件**
1. 固定領域（ヘッダー＋ページヘッダー）の合計高さが、画面高さの 25% を超えない。
2. 760px 幅では固定領域を減らす。

**確認方法** ブラウザで実測。
**自動** 可

## VP-45 スクロールバーの見た目をアプリに合わせる

**書籍** ブラウザ標準のデフォルトの見た目だと、大きすぎたりアプリの印象に合わないことがある。
アプリの文字の大きさや余白に合わせて自然な見た目にし、印象を良くする。

**完了条件**

## VP-59 一般的な一覧はページャーを使い、無限スクロールを避ける

# 書籍外（ISO 9241-110 で補う）

## VP-62 操作には必ず応答を返す

**観点**（自己記述性）
**送信・実行・絞り込みを押した後、押す前と同じ画面を返してはいけない。**
結果が 0 件であることと、機能が動いていないことを、利用者は画面から区別できない。

**完了条件**
1. 検索・絞り込みを未入力／無条件で送信したとき、押す前と異なる文言が出る。
2. その文言に、次に何をすればよいかが書かれている（原因だけで終わらない）。
3. POST 後は必ず結果メッセージ（成功／失敗）を出す。
4. 時間のかかる処理は、処理中であることを示す。

**確認方法** `apps/core/tests/test_empty_submit.py`。
**自動** 可

## VP-63 空・失敗・権限なしの状態を言葉で説明する

**観点**（エラー耐性）

**完了条件**
1. 一覧の 0 件表示に、原因と次の操作がある。「データがありません」だけで終わらせない。
2. 失敗した処理は、失敗理由と再実行の導線を出す。
3. 権限が無い画面は、403 と分かる文言と、戻る導線を出す。
4. 算定不能・未計測を「0」や「正常」と混ぜて表示しない。

**確認方法** 各画面の空状態テスト、`templates/403.html` / `404.html` / `500.html` / `400.html`。
**自動** 可
